# 第11章 組織文化と協働

## 学習目標

- データ活用の意義を業務改善・意思決定・価値創出と関連付けて説明できる。
- DX、データドリブン経営、データマネジメント、データガバナンスの関係を説明できる。
- データに基づく議論へ主体的に参加し、必要な情報と意見を共有できる。
- 部門ごとの要望と、セキュリティや作業負担などの制約を整理し、共通理解を作れる。
- 成功・失敗事例から得た知見を再利用可能な形で組織へ共有できる。

**シラバス対応**：科目B 3-1、3-2。

## 1. ツールだけでは文化は変わらない

BIツールやデータ基盤を導入しても、指標定義が部門で異なる、失敗を共有できない、データの責任が不明、利用者が結果を信用しない状態では活用は定着しません。データ活用の組織文化とは、重要な判断で根拠を確かめ、異論や不確実性も共有し、結果から学ぶ行動が日常化した状態です。

文化は掛け声ではなく、次の循環で形成されます。

```text
業務の問いを立てる
      ↓
根拠となるデータを確認する
      ↓
立場を越えて議論する
      ↓
小さく実行し、結果を測る
      ↓
成功・失敗から学びを共有する
      └────────→ 次の問いへ
```

会議で都合の悪い数値を隠す、失敗した試行の担当者を責める、指標の出所を確認しないといった行動が続けば、制度やツールがあっても文化は育ちません。

## 2. データ活用の意義と関連する取組

データ活用には、経験や直感を否定するのではなく、検証可能な根拠を加える役割があります。

| 目的 | データ活用がもたらすこと | 職場例 |
|---|---|---|
| 業務改善 | ボトルネックや変化を可視化する | 工程別待ち時間から滞留箇所を特定する |
| 意思決定 | 選択肢の効果とリスクを比較する | 出店候補地を商圏人口と既存店実績で比べる |
| 価値創出 | 未充足ニーズや新しい組合せを見つける | 利用履歴から保守サービスを提案する |
| 説明責任 | 判断根拠と結果を追跡できるようにする | 審査基準と承認理由を記録する |
| 組織学習 | 仮説と結果を蓄積し改善速度を上げる | 施策の成功条件と失敗条件を共有する |

データドリブンとは「数字だけで決める」ことではありません。データの限界を理解し、業務知識、倫理、戦略、現場観察と合わせて判断します。

### DXなどとの関係

| 概念 | 主な役割 | データ活用との関係 |
|---|---|---|
| DX | デジタル技術を用いて事業や業務を変革する | データ活用は変革案の発見と効果検証を支える |
| データドリブン経営 | 根拠に基づき継続的に判断する | データを判断と学習へ結び付ける経営・業務の姿勢 |
| データマネジメント | データを資産として整備・維持する | 利用可能で意味の明確なデータを提供する |
| データガバナンス | 方針、責任、権限、監視を定める | 安全で説明可能な活用の境界を作る |

```text
DX（事業・業務の変革）
  └─ データドリブンな意思決定と学習
       ├─ データ活用：問い、分析、実行、検証
       ├─ データマネジメント：品質、定義、所在、ライフサイクル
       └─ データガバナンス：方針、責任、権限、監視
```

例えば需要予測を導入するDX施策では、予測モデルだけでなく、販売・在庫データの品質管理、誰が発注量を最終承認するか、誤予測時の対応ルールまで必要です。

## 3. 関係者の要望と制約を理解する

同じデータ活用でも、立場によって成功の意味が異なります。

| 関係者 | 主な要望 | 主な制約・懸念 |
|---|---|---|
| 経営・業務責任者 | 効果、速い判断、説明責任 | 予算、優先順位、事業リスク |
| 業務担当者 | 実態との一致、使いやすさ | 入力・確認の作業負担、繁忙期 |
| データ主管組織 | 標準化、全社最適、再利用 | 品質、所有者、統制との整合 |
| IT部門 | 安定した実装・運用 | 既存連携、保守要員、セキュリティ |
| 法務・コンプライアンス | 適法で公正な利用 | 法令、契約、権利、社会的影響 |
| 分析担当者 | 分析可能なデータと明確な問い | 欠損、偏り、評価期間、再現性 |

制約を「データ活用への抵抗」と片付けてはいけません。例えば営業部が顧客データ共有に慎重なのは、入力負担だけでなく、契約上の利用目的や顧客との信頼を懸念している可能性があります。背景を聞き、目的を満たす代替案を探します。

### 制約を解消又は軽減する例

| 制約 | 性急で不適切な対応 | 対話による対応例 |
|---|---|---|
| セキュリティ | 全員へ広い権限を付ける | 項目を限定し、役割別権限と利用記録を設ける |
| 作業負担 | 現場へ追加入力を一方的に求める | 既存入力から自動取得し、必要最小限だけ追加する |
| 指標定義の差 | 一方の定義を正解とする | 用途を確認し、共通定義又は用途別定義を合意する |
| 品質不足 | 担当部門を責める | 発生工程と業務影響を確認し、予防策を共同設計する |

## 4. データに基づく議論へ参加する

主体的な参加とは、分析担当者へ全て任せることでも、専門用語で競うことでもありません。業務担当者は、現場でのデータ生成背景、例外、結果の実行可能性を提供できます。

### 会議前・会議中・会議後の行動

| 場面 | 行動 |
|---|---|
| 会議前 | 問い、指標定義、対象期間、出所、更新時点を確認する |
| 会議中 | 事実と意見を分け、前提・不確実性・例外を共有する |
| 意見対立時 | 定義、分母、粒度、除外条件を比較し、検証方法を決める |
| 会議後 | 決定、保留事項、担当、期限、利用データを記録する |

発言は「この数字は違う」ではなく、「店舗閉鎖日を分母から除外していますか。現場の稼働率と差が出る可能性があります」のように、確認可能な形にします。

## 5. 共通理解を作る対話

1. 解決したい業務課題と、必要な判断を共有する。
2. 用語、指標、対象、期間、粒度を確認する。
3. 必要なデータ、データオーナー、生成過程を特定する。
4. セキュリティ、法務、作業負担、品質の制約を整理する。
5. 代替案と、各案で残るリスクを比較する。
6. 役割、最終判断者、期限、エスカレーション先を決める。
7. 小さく試し、結果と教訓を共有する。

### 職場例：二つの「月次売上」

営業部は受注時点、経理部は出荷・請求条件を満たした時点で売上を集計していました。どちらかが単純に誤りなのではなく、営業見込み管理と会計報告という用途が異なります。

```text
顧客の注文 → 受注 → 出荷 → 請求 → 入金
                │       │
                │       └─ 経理の月次売上
                └─ 営業の受注実績
```

両部門は、名称を「受注実績」と「会計売上」に分け、対象期間、取消・返品、税、更新時点をグロッサリーへ登録しました。経営会議では利用目的に合う指標を明示します。無理に一つの値へ統一するより、違いの意味を管理する方が適切な場合もあります。

## 6. データ共有・統合へ協力する

組織横断の活用では、各部門が保有するデータの対応関係を確認する必要があります。共有はファイルを渡すだけでは完了しません。

| 確認事項 | 具体例 |
|---|---|
| 目的 | 需要予測のため。人事評価へ転用しない |
| 定義・粒度 | 顧客企業単位か事業所単位か |
| 対応キー | 顧客IDの体系、統合・分割履歴 |
| 品質・更新 | 欠損率、更新頻度、締め処理 |
| 権限・責任 | 提供者、利用者、承認者、問合せ先 |
| 保管・廃棄 | 管理場所、保存期間、終了時の削除 |

営業の顧客IDとサポート部門の契約IDを名称だけで結合すると、同名企業や複数契約で誤集計が起きます。業務担当者は、IDの生成・変更ルールや例外を説明し、データ主管組織の統合作業へ協力します。

## 7. 成功・失敗事例を組織知にする

「成果が出た」という報告だけでは再現できません。次の項目を整理します。

- 課題、対象業務、利用者
- 仮説と選定データ
- 前提、品質、制約
- 実施内容と役割分担
- 結果、測定方法、比較対象
- 想定外、失敗、副作用
- 成功・不成立となった条件
- 再利用できる範囲
- 次回の改善

### 共有例：予測発注の失敗

ある店舗で予測発注により廃棄が減ったため、別店舗へそのまま展開しました。しかし、イベント会場に近い店舗では突発需要が多く、欠品が増えました。この事例で共有すべき教訓は「予測は使えない」ではなく、「定常需要が多い店舗では有効だが、イベント情報を扱えない現状では変動の大きい店舗にそのまま適用しない」です。適用条件を示して初めて、失敗が組織知になります。

## 8. 定着のための仕組み

| 仕組み | 日常行動への組込み方 |
|---|---|
| データオーナーと相談窓口 | ダッシュボードから問合せ先を確認できるようにする |
| グロッサリーとカタログ | 会議資料に指標定義へのリンクを付ける |
| 品質問題の報告 | 責任追及ではなく影響・原因・暫定対応を記録する |
| 実務型研修 | 自部門の課題とデータを用いて小さく分析する |
| 事例リポジトリ | 成功だけでなく不成立条件と検索用タグを残す |
| 定期的な見直し | 利用率、作業負担、統制効果を確認する |

指標の数やツール利用回数だけを評価すると、不要なダッシュボードや形式的な利用が増えるおそれがあります。業務上の成果、判断の質、再利用された教訓なども確認します。

## 9. データ文化の成熟度を段階で捉える

文化は「ある・ない」の二択ではありません。同じ組織でも、会議で数値を参照する習慣は定着している一方、指標の定義管理や失敗からの学習は弱い場合があります。成熟度は人を格付けするためではなく、次に変えるべき行動と仕組みを選ぶために使います。

| 段階 | 典型的な行動 | 判断・学習の状態 | 次の改善 |
|---|---|---|---|
| 1. 個人依存 | 詳しい人が個別に表計算する | 根拠や手順を再現しにくい | 問い、出所、計算方法を記録する |
| 2. 部門最適 | 部門内では共通指標を使う | 部門間で定義や優先順位が衝突する | 用途別定義と責任者を合意する |
| 3. 標準化 | カタログ、品質管理、会議様式がある | 標準への形式的な準拠が起こり得る | 利用者負荷と業務成果を測る |
| 4. 協働・学習 | 異論、失敗、適用条件を共有する | 仮説検証が部門を越えて再利用される | インセンティブと権限を継続的に見直す |
| 5. 適応 | 戦略や環境変化に応じて指標と統制を変える | 成果と副作用を監視し、自律的に改善する | 過剰統制や指標の形骸化を防ぐ |

成熟は一直線には進みません。新設部門、企業統合、法改正、基盤更新によって一部の能力が後退することもあります。そのため、全社を一つの段階に決め付けず、「定義管理」「会議行動」「学習共有」などの観点別に現在地を確認します。

```text
個人依存 → 部門最適 → 標準化 → 協働・学習 → 適応
   │           │           │             │          │
 手順記録    定義調整    成果を確認    異論を活用   環境変化へ更新
   └──────── 制度だけでなく日常行動を観察 ────────┘
```

## 10. インセンティブと心理的安全性

「データを使おう」と呼び掛けても、短期売上だけで評価される営業担当者が品質問題の報告に時間を使うとは限りません。望ましい行動に必要な時間、権限、評価をそろえる必要があります。

| 望ましい行動 | 阻害するインセンティブ | 仕組みの改善例 |
|---|---|---|
| 品質問題を早期報告する | 報告件数が多い部門を低評価する | 早期検知、影響抑制、再発防止への貢献を評価する |
| 部門横断でデータを共有する | データ保有を部門の権力とみなす | 再利用件数だけでなく、安全な提供と支援を評価する |
| 不確実性や反証を示す | 上司の案への異論が不利益になる | 代替仮説と検証提案を会議様式に含める |
| 定義や手順を文書化する | 目先の納期だけを評価する | 文書化を完了条件と工数計画へ組み込む |
| 効果のない施策を止める | 中止を失敗とみなす | 損失回避と得られた知見を評価する |

心理的安全性とは、何を言っても責任を問われない状態ではありません。疑問、誤り、未確認事項を対人リスクなく表明でき、その後に事実確認と是正へ進める状態です。安全性と説明責任を両立させるには、人ではなく仮説・過程・影響を検討し、故意の規程違反と善意の試行錯誤を区別します。

リーダーは、最初に自分の前提と不確実性を明示し、反対意見を述べた人へ根拠を尋ね、悪い知らせを早く出した行動を認めます。会議後に異論を述べた人へ不利益が生じていないかも確認します。発言を募るだけで実際の扱いが変わらなければ、安全性は形成されません。

## 11. 採用指標と成果指標をつなぐ

定着を測るときは、仕組みが使われたかを示す**採用指標**と、判断や業務が改善したかを示す**成果指標**を分けます。採用は成果の前提になり得ますが、利用回数の増加だけでは価値を証明できません。

| 指標層 | 例 | 読み方と注意点 |
|---|---|---|
| 到達 | 研修受講率、権限付与率 | 利用可能になっただけで、実利用とは限らない |
| 採用 | 月間利用者率、会議での参照率 | 強制利用や重複閲覧で水増しされ得る |
| 行動変化 | 定義確認率、仮説記録率、品質問題の早期報告率 | 望ましい手順が日常化したかを見る |
| 意思決定 | 判断所要日数、保留理由の明確さ、再検討率 | 速さだけでなく質と説明可能性も確認する |
| 業務成果 | 手戻り、欠品、解約、処理費用 | 外部要因や他施策の影響を分けて考える |
| 健全性 | 入力負荷、例外件数、異論の件数、利用者信頼度 | 成果の陰で負担や沈黙が増えていないかを見る |

指標には基準値、対象者、測定期間、比較対象を置きます。例えば利用率が上がっても、会議資料への添付が義務化されただけなら意思決定は変わっていない可能性があります。ログ、会議記録、利用者インタビュー、業務成果を組み合わせ、因果を断定し過ぎないことが重要です。

### 職場例（計算）：店舗会議の意思決定を改善する

60人の店長を対象に、共通ダッシュボードと指標定義へのリンクを導入しました。導入前後8週間を同じ繁忙度の期間で比べたところ、月間利用者は18人から45人、在庫調整の決定所要日数は平均5日から3日、月間の発注手戻りは120件から84件になりました。

| 測定項目 | 導入前 | 導入後 | 変化 |
|---|---:|---:|---:|
| 月間利用者率 | 18 / 60 = 30% | 45 / 60 = 75% | 45ポイント増 |
| 決定所要日数 | 5日 | 3日 | 40%短縮 |
| 発注手戻り | 120件 | 84件 | 30%減少 |

利用の増加と成果の改善が同時に見られましたが、これだけでダッシュボードが唯一の原因とは断定できません。会議進行の変更や季節要因も確認します。また、利用率100%を個人評価にすると形式的な閲覧を誘発するため、店長を責める材料にはせず、未利用者への聞き取りから権限不足や指標への不信を改善します。

## 12. データを巡る対立を解決する

対立は協働の失敗とは限りません。営業は機会損失、セキュリティ部門は漏えい、現場は作業負荷を重く見るため、合理的な優先順位が異なります。立場の勝敗ではなく、共同で検証できる争点へ変換します。

```text
主張の衝突
  ↓  「なぜ必要か」を聞く
共通目的と利害を分ける
  ↓
事実／定義／価値判断／制約に争点を分類
  ↓
不足データを検証し、複数案と残存リスクを比較
  ↓
決定権者が期限内に判断 ─→ 決定理由を記録
  ↓                           │
結果を測定し、再検討条件に達したら見直す ←┘
```

| 対立の種類 | 例 | 解決方法 |
|---|---|---|
| 事実 | 欠品率が増えたか | 出所、期間、分母を合わせて再計算する |
| 定義 | 「有効顧客」の意味が違う | 用途を明示し、共通又は用途別定義を決める |
| 価値判断 | 速度と精度のどちらを優先するか | 影響と許容範囲を示し、権限者が判断する |
| 制約 | 法令上共有できない項目がある | 目的を保つ代替データや集計方法を探す |
| 利害 | 部門の負担と便益が偏る | 費用・人員配分や評価制度を調整する |

合意できない場合は、期限、決定権者、エスカレーション先を使います。「全員が納得するまで保留」は責任の先送りになり得ます。一方、役職だけで押し切ると重要な現場知識が失われます。決定後も、どの条件なら見直すかを残すことで、異論を将来の検証材料にできます。

## 確認問題（本書オリジナル）

### 問1

営業部と経理部の月次売上が一致しません。協働の第一歩として何を行いますか。

**解答例：** 受注・出荷・請求・入金のどの時点を売上とするか、対象期間、取消・返品、税、更新時点、粒度を比較し、各数値の利用目的と責任者を確認します。用途の違いが差の原因かもしれないためです。「経理の数字に統一する」のは営業管理の目的を満たさない可能性があるため不適切です。「平均を取る」のも、定義の不一致を解消せず意味のない値を作るため不適切です。

### 問2

顧客データを使う横断プロジェクトで、法務部門が共有範囲の縮小を求め、分析担当者は精度低下を懸念しています。進め方を説明してください。

**解答例：** 利用目的、必要項目、契約・法令上の条件、精度への影響を共同で確認し、項目削減、仮名化、集計化、限定環境、役割別権限などの代替案を比較します。要望と制約を可視化すれば、目的を保ちながらリスクを軽減できるためです。「精度優先で全項目を共有する」のは利用条件を無視するため不適切です。「法務が反対したので中止する」のも、適法な代替案を検討していないため不適切です。

### 問3

ある部門のAI議事録作成が好評だったため、全社展開を提案することになりました。どの情報を共有すべきですか。

**解答例：** 対象会議、評価方法、時間短縮、誤記の種類、確認負荷、機密情報の扱い、利用者、費用、適用できない会議、運用上の教訓を共有します。結果だけでなく条件と副作用がなければ、他部門で再現できるか判断できないためです。「利用者の好評コメントだけを示す」のは測定根拠とリスクが不足するため不適切です。「成功した設定を全会議へそのまま適用する」のも、機密度や専門用語の違いを無視するため不適切です。

### 問4

全社員のダッシュボード利用率を人事評価へ組み込んだ結果、月間利用率は95%になりました。しかし、会議の決定時間と手戻り件数は変わらず、品質問題の報告は減りました。この結果をどう評価し、何を改善しますか。

**解答例：** 採用指標は上がったものの、意思決定と業務成果は改善しておらず、品質問題の減少は改善ではなく報告回避の可能性があると評価します。閲覧ログだけでなく、利用目的、会議での参照方法、未報告問題、現場負荷を聞き取り、利用率を直接評価する制度を見直します。その上で、定義確認や早期報告、問題解決への貢献を評価し、発言者が不利益を受けない扱いを整えます。なぜなら、指標とインセンティブが行動をゆがめ、心理的安全性を下げることがあるためです。「95%なので文化が成熟した」と判断するのは採用を成果と取り違えているため不適切です。「利用率の目標を100%へ上げる」のも形式的な閲覧と問題の隠蔽を強めるおそれがあり不適切です。

## まとめ

- データ文化は、ツールではなく役割・対話・日常行動・学習の循環で定着する。
- 成熟度は観点別に捉え、望ましい行動と評価制度をそろえ、心理的安全性と説明責任を両立させる。
- データ活用は、データマネジメントとデータガバナンスに支えられ、DXやデータドリブン経営へつながる。
- 部門差は抵抗と決め付けず、争点を事実・定義・価値判断・制約・利害に分けて調整する。
- 業務担当者はデータに基づく議論と組織横断の共有・統合へ主体的に参加する。
- 採用指標だけでなく、行動変化、意思決定、業務成果、健全性を組み合わせて定着を測る。
- 成功と失敗の条件を記録し、再利用可能な組織知にする。
