# 第6章 データモデルとデータ統合

## 学習目標

- 概念・論理データモデルの役割を説明できる。
- エンティティ、属性、関係、主キー、外部キーを読み取れる。
- 複数データの粒度、範囲、識別子、形式を比較できる。
- 根本的な識別問題と表面的な形式問題を区別できる。

**シラバス対応**：科目A・その他分野「データベース」、科目B 1-2。

## 1. モデルは業務とデータをつなぐ

データモデルは、業務上の対象、その性質、対象間の関係を整理したものです。

- **概念データモデル**：顧客、契約、商品など、業務上の主要概念と関係を示す。
- **論理データモデル**：属性、識別子、正規化された関係などを、特定製品に依存しない形で詳細化する。
- **物理データモデル**：テーブル、列、型、索引など、実装へ落とし込む。

シラバス案は概念・論理モデル、E-R図、UMLを用語例としています。本試験の対象者には、複雑なDB設計より、モデルの意図を理解して業務上の不整合を説明する力が重要です。

## 2. E-R図の基本

- **エンティティ**：管理対象。例：顧客、注文、商品。
- **属性**：対象の性質。例：顧客名、注文日。
- **主キー**：エンティティの各実体を一意に識別する項目。
- **外部キー**：別エンティティの主キーを参照し、関係を表す項目。
- **カーディナリティ**：1対1、1対多、多対多などの関係数。

```text
顧客 1 ─── 多 注文 1 ─── 多 注文明細 多 ─── 1 商品
```

注文と商品を直接結び付けるだけでは、数量や単価をどこに持つか説明できません。注文明細という関係上の単位が必要です。

## 3. 統合前の比較

複数データを結合する前に次を比較します。

| 観点 | 確認例 |
|---|---|
| 意味 | 同じ「売上」が受注額か入金額か |
| 粒度 | 顧客単位か契約単位か |
| 範囲 | 国内のみか、解約顧客を含むか |
| 時点 | 現在値か月末スナップショットか |
| 識別子 | 全社一意かシステム内一意か |
| 形式 | 電話番号のハイフン、日付、文字コード |
| 制約 | NULL、一意性、許容コード |
| 品質 | 欠損、重複、誤入力の程度 |
| 利用条件 | 個人情報、第三者提供、目的制限 |

## 4. 形式一致と意味一致

電話番号のハイフンを除去すれば形式は揃います。しかし、それが本人確認済みで一意か、家族共用や再割当てがあるかによって、顧客識別子としての妥当性は変わります。

逆に、二つの「顧客ID」がどちらも主キーでも、別々のシステムが独自発番していれば、値が同じことに意味はありません。主キーは表の中で一意であることを保証しますが、組織横断で同じ対象を示す保証ではありません。

## 5. 名寄せとマスターデータ

名寄せは、氏名、住所、電話番号など複数属性を正規化・比較し、同一対象らしさを判定します。

注意点：

- 同姓同名を誤結合する偽陽性
- 表記ゆれにより結合できない偽陰性
- 属性の変更、欠損、共有
- 閾値と人手確認
- 個人情報利用の権限と目的
- 判定ルールと結果の説明可能性

恒久的には、全社顧客ID、対応表、マスターデータ管理などを検討します。暫定的に別属性で結合する場合は、精度、対象外、誤判定リスクを明示します。

## 6. データフローとアーキテクチャ

どのシステムが正本か、どこで加工され、誰へ提供されるかを可視化します。データフローは、品質問題の伝播、権限制御、更新遅延、責任境界を理解する助けになります。サブジェクトエリアモデルは、顧客、商品、会計など大きな業務領域でデータを整理します。

## 確認問題（本書オリジナル）

ECと店舗の顧客表には、それぞれ重複しない顧客IDがあります。この二つをIDで結合できない理由を説明してください。

**解答例：** 一意性の範囲が各システム内に限られ、同じ顧客へ共通のIDが割り当てられている保証がないためです。組織横断の識別子または妥当な対応付けルールが必要です。

## まとめ

- モデルはデータ構造の背後にある業務上の意味を示す。
- 統合前に意味、粒度、範囲、時点、識別子、品質、利用条件を比較する。
- 形式を揃える処理と、同じ対象を識別する仕組みは別問題である。
