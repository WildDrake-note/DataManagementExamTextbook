# 第6章 データモデルとデータ統合

## 学習目標

- 概念・論理データモデルの役割を説明できる。
- エンティティ、属性、関係、主キー、外部キーを読み取れる。
- 複数データの粒度、範囲、識別子、形式を比較できる。
- 根本的な識別問題と表面的な形式問題を区別できる。

**シラバス対応**：科目A・その他分野「データベース」、科目B 1-2。

## 1. モデルは業務とデータをつなぐ

データモデルは、業務上の対象、その性質、対象間の関係を整理したものです。

| モデル | 主な目的 | 表す内容 | 読み手の問い |
|---|---|---|---|
| 概念データモデル | 業務の全体像を共有する | 顧客、契約、商品などの主要概念と関係 | 何を管理し、概念同士はどう関係するか |
| 論理データモデル | 要件をデータ構造へ詳細化する | 属性、識別子、正規化された関係 | 何で識別し、どの属性をどこへ持つか |
| 物理データモデル | 特定環境へ実装する | テーブル、列、型、索引、配置 | どの製品・構成で性能と運用を実現するか |

シラバス案は概念・論理モデル、E-R図、UMLを用語例としています。本試験の対象者には、複雑なDB設計より、モデルの意図を理解して業務上の不整合を説明する力が重要です。

## 2. E-R図の基本

- **エンティティ**：管理対象。例：顧客、注文、商品。
- **属性**：対象の性質。例：顧客名、注文日。
- **主キー**：エンティティの各実体を一意に識別する項目。
- **外部キー**：別エンティティの主キーを参照し、関係を表す項目。
- **カーディナリティ**：1対1、1対多、多対多などの関係数。

```text
顧客 1 ─── 多 注文 1 ─── 多 注文明細 多 ─── 1 商品
```

注文と商品を直接結び付けるだけでは、数量や単価をどこに持つか説明できません。注文明細という関係上の単位が必要です。

UMLのクラス図でも、クラス、属性、関連、多重度を用いて似た構造を表せます。表記法が違っても、「一つの顧客は注文を0件以上持てる」「各注文は必ず一つの顧客に属する」のように、最小数と最大数を業務ルールとして読めることが重要です。

| 多重度の例 | 意味 | 確認すべき業務ルール |
|---|---|---|
| `1` | 必ず一つ | 注文は顧客なしで登録できないか |
| `0..1` | なくてもよく、最大一つ | 解約日は未解約なら空でよいか |
| `0..*` | 0件以上 | 顧客は注文履歴がなくても登録できるか |
| `1..*` | 1件以上 | 注文は最低一つの明細を必要とするか |

## 3. 統合前の比較

複数データを結合する前に次を比較します。

| 観点 | 確認例 |
|---|---|
| 意味 | 同じ「売上」が受注額か入金額か |
| 粒度 | 顧客単位か契約単位か |
| 範囲 | 国内のみか、解約顧客を含むか |
| 時点 | 現在値か月末スナップショットか |
| 識別子 | 全社一意かシステム内一意か |
| 形式 | 電話番号のハイフン、日付、文字コード |
| 制約 | NULL、一意性、許容コード |
| 品質 | 欠損、重複、誤入力の程度 |
| 利用条件 | 個人情報、第三者提供、目的制限 |

## 4. 形式一致と意味一致

電話番号のハイフンを除去すれば形式は揃います。しかし、それが本人確認済みで一意か、家族共用や再割当てがあるかによって、顧客識別子としての妥当性は変わります。

逆に、二つの「顧客ID」がどちらも主キーでも、別々のシステムが独自発番していれば、値が同じことに意味はありません。主キーは表の中で一意であることを保証しますが、組織横断で同じ対象を示す保証ではありません。

## 5. 名寄せとマスターデータ

名寄せは、氏名、住所、電話番号など複数属性を正規化・比較し、同一対象らしさを判定します。

注意点：

- 同姓同名を誤結合する偽陽性
- 表記ゆれにより結合できない偽陰性
- 属性の変更、欠損、共有
- 閾値と人手確認
- 個人情報利用の権限と目的
- 判定ルールと結果の説明可能性

恒久的には、全社顧客ID、対応表、マスターデータ管理などを検討します。暫定的に別属性で結合する場合は、精度、対象外、誤判定リスクを明示します。

## 6. データフローとアーキテクチャ

どのシステムが正本か、どこで加工され、誰へ提供されるかを可視化します。データフローは、品質問題の伝播、権限制御、更新遅延、責任境界を理解する助けになります。サブジェクトエリアモデルは、顧客、商品、会計など大きな業務領域でデータを整理します。

```text
[営業システム] --顧客・受注--> [統合処理] --> [DWH] --> [営業BI]
      正本候補                     │             └--> [需要予測]
                                  └--エラー記録--> [運用監視]
```

矢印には、データ名、頻度、変換、責任者、失敗時の扱いを付けます。「システムAからDWHへ」のような箱と矢印だけでは、どの粒度のデータがいつ届き、失敗時に前回値が残るのかを判断できません。

**実例：月次売上の誤集計**

店舗データは店舗・日単位、ECデータは注文単位であり、さらに店舗の「売上」は税込、ECは税抜だったとします。列名をそろえて単純に結合すると、粒度と定義の差により比較を誤ります。共通の分析粒度と金額定義を決め、変換ルール、対応キー、対象期間、除外条件を記録してから統合します。

## 7. サブジェクトエリアで責任境界を設計する

サブジェクトエリアは、単なるシステム一覧ではなく、顧客、商品、契約、販売、会計など、比較的安定した業務概念のまとまりです。各領域について正本、責任者、共通識別子、他領域との受渡しを定めると、システム更改があっても全体構造を説明しやすくなります。

```text
                共通顧客ID                 共通商品ID
[顧客エリア] 1 ───────── 多 [販売エリア] 多 ───────── 1 [商品エリア]
     │                         │                          │
     │ 顧客区分                │ 注文・明細               │ 商品分類
     v                         v                          v
[マーケティング]          [会計エリア] <──仕訳規則── [価格・税ルール]

境界を越える受渡しごとに、意味・粒度・キー・頻度・責任者を定義する。
```

| 設計項目 | 顧客エリアの例 | 販売エリアの例 | 境界で確認すること |
|---|---|---|---|
| 中心となる対象 | 顧客、世帯、連絡先 | 注文、注文明細、返品 | 顧客と注文の対応数 |
| 正本 | 顧客マスター | 受注管理 | 更新競合時の優先元 |
| 基本粒度 | 顧客1件 | 注文明細1件 | 集計前後の粒度 |
| 共通キー | 全社顧客ID | 注文ID＋明細番号 | ローカルIDとの対応表 |
| 責任者 | 顧客管理部門 | 営業業務部門 | 不一致の判断者 |

領域を細かく分けすぎると受渡しが増え、逆に「全社データ」の一領域へまとめると責任が曖昧になります。業務上の意思決定、ライフサイクル、責任者がまとまる単位を基準に境界を置きます。

## 8. マッピング仕様は統合契約である

マッピング仕様は「元列Aを先列Bへコピーする」一覧ではありません。意味、粒度、識別子、変換、品質、例外処理を、提供側と受入側が検証できる形で記述した統合契約です。

| 項目 | 記述例 | 検証観点 |
|---|---|---|
| 元・先 | `ORDER_LINE.qty` → `sales_line.quantity` | 型、NULL可否、単位が一致するか |
| 業務定義 | 確定済み明細の販売数量 | 取消・返品を含むか |
| 粒度 | 注文ID＋明細番号につき1行 | キー重複がないか |
| 変換式 | `qty * unit_price`、端数は明細ごとに切捨て | 境界値と丸め順序は正しいか |
| 参照対応 | 店舗商品コードを共通商品IDへ変換 | 未対応コードをどう扱うか |
| 時点・頻度 | 毎日02:00、前日確定分 | 遅着・再送時に重複しないか |
| 例外処理 | 不正値は隔離し処理件数へ計上 | 黙ってNULLや0へ変えないか |
| 照合条件 | 入力件数＝出力＋隔離、金額差0円 | 完了を客観的に判定できるか |

変換仕様には正常例だけでなく、NULL、未知コード、重複、遅着、取消し、再実行を含めます。仕様にない値を便宜的に0へ変えると処理は成功して見えますが、欠損と実際の0を区別できなくなります。

## 9. 統合パターンを目的で使い分ける

| パターン | 特徴 | 適する場面 | 主な注意点 |
|---|---|---|---|
| バッチETL/ELT | 一定期間分をまとめて抽出・変換 | 日次集計、履歴蓄積 | 遅延、再実行、二重取込 |
| CDC | 追加・変更・削除を継続取得 | 正本の変更追随 | 更新順序、削除表現、取りこぼし |
| メッセージ／イベント | 発生事実を非同期配信 | 注文発生など即時連携 | 重複配信、順序、冪等性 |
| API連携 | 要求時に最新情報を取得・更新 | 顧客照会、在庫引当 | タイムアウト、契約版、呼出し制限 |
| データ仮想化 | 元データを移さず論理的に参照 | 横断検索、短期的な統合 | 元性能、可用性、意味の統一 |

どの方式でも識別子や定義の不一致は自動では解決しません。リアルタイム化は鮮度を上げますが、誤った対応付けを速く広げる可能性もあります。配信方式と意味統合を別々に設計します。

## 10. 粒度とカーディナリティによる誤集計を防ぐ

結合前に各表の「1行が何を表すか」を一文で書き、候補キーの一意性と結合後の件数を検証します。特に、1対多の表を二つ同時に親表へ結合すると、多対多の組合せが生じて金額が水増しされます。

**実例：キャンペーン別売上の水増し**

ある注文に明細が2件、適用キャンペーンが3件あるとします。注文をキーに明細表とキャンペーン表を直接結合すると、`2 × 3 = 6` 行になります。明細金額100円と200円が各3回現れ、単純合計は本来の300円ではなく900円です。

```text
注文 O1
 ├─ 明細: L1=100円, L2=200円       （注文1 : 明細2）
 └─ 施策: C1, C2, C3              （注文1 : 施策3）

危険な結合: 注文 ─ 明細 ─ 施策
             2行 × 3行 = 6行 → 売上が3倍

安全な例  : 明細を注文単位へ集計 ─┐
             施策数を注文単位へ集計 ─┴→ 注文単位同士を結合
```

| 検査 | 実施方法 | 発見できる問題 |
|---|---|---|
| 粒度宣言 | 「1行＝注文の1明細」のように明記 | 異なる単位の混同 |
| キー一意性 | 候補キー別の件数と重複数を確認 | 想定外の多側 |
| 結合前後件数 | 親件数、結合件数、未対応件数を比較 | 行の増殖・欠落 |
| 金額照合 | 元合計と統合後合計を範囲別に比較 | 重複加算、除外漏れ |
| カーディナリティ制約 | 期待する1対1、1対多をテスト | マスター重複、対応表の期間重複 |

複数キャンペーンへ売上を配賦したい場合は、先に配賦ルールを決め、キャンペーン別比率の合計が1になることを検証します。重複を見つけてから `DISTINCT` で消す方法は、正当な同額明細まで消したり、どの関係が誤っていたかを隠したりするため、根本対策ではありません。

## 確認問題（本書オリジナル）

### 問1

ECと店舗の顧客表には、それぞれ重複しない顧客IDがあります。この二つをIDで結合できない理由を説明してください。

**解答例：** 一意性の範囲が各システム内に限られ、同じ顧客へ共通のIDが割り当てられている保証がないためです。組織横断の識別子または妥当な対応付けルールが必要です。「どちらも主キーだから結合できる」という判断は、主キーの有効範囲を取り違えているため不適切です。

### 問2

「顧客1―多 注文」という関係から読み取るべき業務ルールを挙げ、図だけでは不足する点を説明してください。

**解答例：** 一人の顧客に複数注文が対応し、各注文は一人の顧客へ対応することを表します。ただし、注文0件の顧客を許すか、顧客未確定の注文を許すかは最小多重度の確認が必要です。「多」を見て件数上限まで決まったと考えるのは不適切です。

### 問3

二つの売上表で日付形式と通貨表記を統一しました。これだけで安全に統合できない理由を説明してください。

**解答例：** 売上の定義、税込・税抜、受注・入金の別、粒度、対象範囲、取消しの扱い、識別子、利用条件が一致するとは限りません。形式統一は必要でも意味一致を保証しません。列型が一致したことだけを統合可否の根拠にする方法は不適切です。

### 問4

注文表（1注文1行）へ、注文明細表（1注文に複数行）と決済表（分割払いにより1注文に複数行）を注文IDで結合したところ、売上合計が増えました。原因の確認方法と修正方針を説明してください。

**解答例：** まず各表の1行の意味と候補キーを明記し、注文IDごとの明細件数・決済件数、結合前後の行数と金額を照合します。明細と決済がともに注文の多側なら、直接結合によって明細件数×決済件数の組合せが生じています。分析目的が注文単位なら、それぞれを注文単位へ集計してから1対1で結合します。明細と決済の対応が必要なら、決済配賦を表す橋渡し表と配賦ルールを設計し、比率合計を検証します。最後に期待カーディナリティ、未対応件数、元合計との一致を自動テストします。結合後に `DISTINCT` をかける方法は、正当な複数明細を消す可能性があり、粒度の不一致を解決しないため不適切です。

## まとめ

- モデルはデータ構造の背後にある業務上の意味を示す。
- 統合前に意味、粒度、範囲、時点、識別子、品質、利用条件を比較する。
- 形式を揃える処理と、同じ対象を識別する仕組みは別問題である。
- サブジェクトエリアの境界とマッピング仕様で、正本、責任、受渡し条件を明確にする。
- 結合前に粒度とカーディナリティを宣言し、件数・金額の照合で行の増殖を防ぐ。
