# 第8章 AIと非構造化データ

## 学習目標

- 識別AI、生成AI、AIエージェントの利用上の違いを説明できる。
- AIへの入力・出力に関するデータリスクを判断できる。
- 非構造化データの探索性、再利用性、版管理を改善できる。

**シラバス対応**：科目A・重点分野「AI利活用」、その他分野「AI倫理・AIガバナンス」、科目B 1-5、1-6。

## 1. AI利活用の基本

AIの性能だけでなく、目的、データ、利用者、影響、人間の関与を含むシステム全体を管理します。人間中心、公平性、安全性、プライバシー、透明性、アカウンタビリティなどの原則を、具体的な業務手順へ落とし込む必要があります。

日本の「人間中心のAI社会原則」は、人間の尊厳、多様性・包摂性、持続可能性などを重視します。「AI-readyな社会」とは、AIを導入するだけでなく、制度、データ、業務、教育をAIの便益とリスクに対応できる状態へ整える考え方です。実務ではAI事業者ガイドラインなどを参照し、自組織の役割と業務手順へ具体化します。

## 2. AIの類型とデータ

三つの類型は排他的ではありません。一つの業務システムが、識別AIで分類し、生成AIで文章を作り、AIエージェントが登録処理まで行うこともあります。出力がそのまま実行へつながるほど、誤りの影響と必要な統制は大きくなります。

| 類型 | 主な出力・動作 | 職場での例 | 特に確認する点 |
|---|---|---|---|
| 識別AI | 分類、予測、数値評価 | 不良品判定、需要予測、解約予測 | 学習データの偏り、精度、誤判定の影響 |
| 生成AI | 新しい文章、画像、音声、コード | 議事録要約、提案文、プログラム案 | 誤情報、出典、入力情報、知的財産 |
| AIエージェント | 目標に沿った手順選択とツール操作 | メール下書き、在庫照会、会計登録 | 権限、承認、例外処理、ログ、停止手段 |

### 識別AI

教師あり学習による予測、教師なし学習によるグルーピング、強化学習による意思決定支援などがあります。仮説検証、知識発見、原因究明、判断支援、作業の代替などに使われます。学習データが過去の偏りを含む場合、結果も偏る可能性があります。

**実例：解約予測**

顧客が翌月に解約する確率を予測し、担当者の優先順位付けを支援します。予測値だけで自動的に不利益な処遇を決めず、目的、誤判定の影響、利用項目の妥当性、人間による確認を定めます。

### 生成AI

文章、画像、音声、コードなどを生成します。主な留意点は次です。

- もっともらしい誤情報（ハルシネーション）
- 学習・参照データの偏り
- 機密情報・個人情報の入力
- 著作権・ライセンス
- 出力の出典・根拠
- プロンプトインジェクション等の攻撃

生成AIには、文章・画像・音声など複数の形式を扱うマルチモーダルAIがあります。文章の添削・要約、アイデア提案、情報収集、プログラミング、画像・動画・音声生成などに利用できますが、用途ごとに必要な検証は異なります。

プロンプトエンジニアリングは、目的、前提、制約、出力形式、例などを指示して出力を調整する方法です。システムプロンプトは、対話全体の役割や制約を設定する指示として使われます。温度などによるランダム性の制御は再現性や多様性へ影響しますが、低い設定にしても正しさは保証されません。複数の生成AIが同じ回答を出したことも、独立した根拠による事実確認の代わりにはなりません。

RAGは外部知識を検索して生成へ利用する仕組みですが、情報源の品質、権限、更新、検索漏れ、引用の正確さを別途管理する必要があります。RAGを使えば必ず正確になるわけではありません。

```text
利用者の質問
      ↓
質問を検索用に変換 → 文書群から候補を検索 → 関連部分をモデルへ渡す
                         │                    │
                    権限・版・漏れを確認      ↓
                                      回答と引用を生成
                                             ↓
                              人が原文と業務ルールを確認
```

RAGでは「検索」と「生成」を分けて点検します。検索が正しい文書を返しても、モデルが読み違えることがあります。逆に生成が忠実でも、検索で旧版しか取得できなければ回答は不適切です。

### AIエージェント

AIがツールやシステムを操作する場合、誤った出力が実際の変更へ直結します。閲覧、下書き、承認付き実行、自律実行など段階を分け、影響が大きい操作には人間の最終承認、権限分離、操作ログ、停止手段を設けます。

AIエージェントをモデル単体ではなく、指示、ツール、権限、記憶、評価、監視、承認、停止機構を含む実行基盤として設計・運用する考え方を、ハーネスエンジニアリングと呼びます。高性能なモデルを選ぶだけでは、安全な業務実行にはなりません。

| 自律性の段階 | AIに任せる範囲 | 人間の関与例 |
|---|---|---|
| 閲覧・提案 | 情報を読み、候補を示す | 人が採否を判断する |
| 下書き | 文書や操作案を作る | 人が修正して送信・実行する |
| 承認付き実行 | 実行直前まで進める | 金額や宛先を人が最終承認する |
| 条件付き自律実行 | 定めた範囲内で自動実行する | 上限超過や例外時だけ人へ戻す |

自律性は一律に高めるものではありません。可逆性が低い操作、金銭・権利・安全に関わる操作、多数の相手へ影響する操作ほど、人間の確認を厚くします。

**実例：請求書処理エージェント**

エージェントが請求書を読み、会計システムへ登録する場合、金額上限、取引先マスタとの照合、重複検知、承認者、例外時の停止先を定めます。閲覧権限しか必要ない工程に更新権限を与えないことも重要です。

## 3. ガードレールと人間の関与

- 入力データの分類・遮断
- 出力形式と禁止事項の制約
- 利用可能ツールと権限の最小化
- 重要判断の人間レビュー
- 例外処理とエスカレーション
- ログ、評価、監視
- 事故時の停止・復旧

ガードレールは万能ではありません。技術制御、規程、教育、契約、監視を組み合わせます。

AI利用を「入力」「処理」「出力」「実行」に分けると、統制の抜けを見つけやすくなります。

| 段階 | 代表的なリスク | 統制例 |
|---|---|---|
| 入力 | 機密情報の漏えい、目的外利用 | データ分類、項目削減、承認済み環境 |
| 処理 | 不適切な参照、外部保存、偏ったモデル | 契約確認、権限付き検索、モデル評価 |
| 出力 | 誤情報、差別的表現、権利侵害 | 根拠照合、人間レビュー、禁止用途 |
| 実行 | 誤送信、誤更新、大量処理 | 最小権限、件数・金額上限、承認、停止機構 |

**人間が確認する**と書くだけでは不十分です。誰が、どの根拠と基準で、いつまでに確認し、問題時にどこへ戻すかまで定めます。大量の出力を形式的に承認するだけなら、実質的な統制になりません。

## 4. AI利用前チェック

1. 目的と期待効果は明確か。
2. 入力データを利用する権利・権限があるか。
3. 個人情報、機密情報、契約制限情報を含まないか。
4. サービス側の保存・学習・国外移転条件は確認したか。
5. 出力の誤り・偏りが与える影響は何か。
6. 誰が検証・承認するか。
7. 利用データ、プロンプト、モデル、結果をどこまで記録するか。

## 5. 非構造化データ

文書、メール、画像、動画、音声などは、表形式データと比べて内容の自動把握、検索、重複判定が難しくなります。ファイル名だけに意味を詰め込むと、命名ゆれや変更で管理できなくなります。

| 課題 | 起こること | 改善の方向 |
|---|---|---|
| 内容を一覧しにくい | 開かないと中身や機密性が分からない | 文書種別、要約、機密区分をメタデータ化する |
| 検索しにくい | 表記ゆれや画像内文字で検索漏れが起こる | 統制語彙、OCR、全文検索を目的に応じて使う |
| 重複しやすい | 添付やコピーごとに別ファイルが増える | 正本を一つにし、共有リンクを使う |
| 版を誤認しやすい | 「最終版」が複数できる | 版番号、承認状態、更新履歴を管理する |
| 関係を追いにくい | 文書と案件・顧客・表データが結び付かない | 共通IDや関連リンクを付ける |

```text
作成 → 分類・命名 → 正本へ登録 → 共有 → 更新・承認 → 保存期限確認
       タグ付け       版を確定       範囲確認   履歴を保持       廃棄又は保管
```

### 管理の要点

- 組織で定めた保管場所を使う。
- 文書種別、業務、顧客、年月、機密区分などのメタデータを付ける。
- 命名規則を統一する。
- 正式版、作業版、過去版を区別する。
- 版番号だけでなく更新履歴と承認状態を管理する。
- 共有先と公開範囲を確認する。
- 重複、散在、孤立ファイルを定期的に整理する。

### タグ設計

タグは自由すぎると表記ゆれが増え、厳格すぎると入力負担が増えます。選択式の統制語彙と自由タグを目的に応じて組み合わせ、廃止・統合ルールを用意します。

非構造化データにも、案件ID、顧客ID、作成日、承認状態などを付与すると、表形式データや他のコンテンツとの対応関係を追跡できます。ただし、誤ったIDや過剰なタグ付けは誤検索や情報漏えいにつながるため、定義と入力ルールを統一します。

**実例：最新版が分からない提案書**

「提案書_最終」「提案書_最終2」「提案書_確定版」が複数の個人フォルダにある状態では、最新版と承認済み版を判定できません。所定の保管場所を一つ定め、文書ID、版、状態、所有者、更新日を管理し、共有リンクは正本を指すようにします。担当者だけで解決できない散在や検索性の問題は、データ主管部門へ改善案を添えて相談します。

## 6. AIシステムの変更を管理する

導入時に評価へ合格したAIでも、モデル、プロンプト、参照文書、検索設定、接続ツール、業務ルールが変われば、出力とリスクが変わります。「同じサービス名だから同じ挙動」と考えず、何が変わったかを記録し、影響に応じて再評価します。

| 変更対象 | 起こり得る影響 | 確認する証拠 |
|---|---|---|
| モデル・版 | 精度、表現、拒否動作、処理費用が変わる | 版、提供者の変更情報、固定評価データの結果 |
| システムプロンプト | 回答方針、禁止事項、出力形式が変わる | 変更差分、承認者、変更前後の評価 |
| RAG文書・検索設定 | 取得文書、権限、引用、検索漏れが変わる | 文書版、索引更新、権限テスト、検索結果 |
| 接続ツール・権限 | 実行可能な操作と影響範囲が変わる | 権限一覧、上限、承認経路、操作ログ |
| 業務ルール | 正しい回答・判断の基準が変わる | 規程の施行日、オーナー承認、利用者周知 |

```text
変更要求 → 変更箇所と影響範囲を特定 → 評価計画 → 限定環境で検証
   │                 │                   │              │
理由・責任者      データ・出力・実行     合格・停止条件   旧版と比較
   └────────────────── 記録・承認 ─────────────────────┘
                                      ↓
                              段階反映 → 監視 → 必要なら戻す
```

### 評価は平均値だけで終わらせない

| 評価観点 | 問い | 指標・確認例 |
|---|---|---|
| 品質 | 目的に必要な結果を出すか | 正答率、重要情報の欠落、引用一致 |
| 安全・公平 | 特定条件で重大な害がないか | 禁止出力、対象群別の誤り、重大事例 |
| 情報管理 | 不要な情報を参照・出力しないか | 権限別テスト、ログ、保存・削除条件 |
| 実行 | 誤りが実操作へ拡大しないか | 承認率、例外率、上限超過、停止テスト |
| 運用 | 人が現実に確認・対応できるか | 確認時間、差戻し、問い合わせ、復旧時間 |

**職場例：規程検索RAGの更新**

人事規程を改定して検索索引を更新した後、代表的な質問だけが正しく答えられても十分ではありません。旧規程を引用しないこと、施行日前後を区別できること、権限のない利用者へ限定規程を表示しないこと、根拠がない質問では断定しないことを評価します。不具合時に旧索引へ戻せるよう、文書版、索引版、プロンプト版、評価結果を対応付けて記録します。

## 7. 非構造化コンテンツとAI生成物のライフサイクル

AIが生成した要約や分類ラベルも、元文書から独立した「正しい事実」ではありません。元文書、生成条件、確認状態、利用期限を結び付けて管理します。

```text
元文書 ──> AI処理 ──> 生成物 ──> 人の確認 ──> 業務利用
  │          │           │            │            │
文書版     モデル版     出力日時     承認状態      利用先
  └──────────── 追跡可能な関連ID ────────────────┘
```

## 確認問題（本書オリジナル）

### 問1

社内規程集をRAGで検索できるチャットボットを導入します。「社内文書だけを参照するので安全で正確」と断定できない理由を挙げてください。

**解答例：** 文書の最新版管理、アクセス権、検索漏れ、誤った文書の取得、生成時の誤要約、引用の不一致、機密情報の出力、利用ログの取扱いなどが残ります。情報源・検索・生成・権限・人間確認を一体で管理します。

**理由：** RAGは参照情報を追加する仕組みであり、文書管理、検索、生成の各段階に誤りが入り得るためです。**不適切な考え方：** 「社内文書なら全部正しい」は旧版や誤記を無視し、「引用が表示されれば正しい」は引用内容と回答の不一致を見落とします。

### 問2

採用候補者の評価を生成AIに行わせ、評価点が一定値未満なら自動で不採用通知を送る案があります。人間の関与とガードレールの観点から問題点を挙げてください。

**解答例：** 入力データや評価基準の偏り、誤評価、説明可能性、不利益な判断の自動実行が問題になります。利用項目と評価基準を確認し、人間による最終判断、送信前承認、操作ログ、異議申立てや例外処理、停止手段を設けます。

**理由：** 採否は個人へ大きな影響を与え、誤りや偏りを送信後に容易に取り消せないためです。**不適切な考え方：** 「AIは人より客観的」は学習データや基準の偏りを無視します。「人が後で抜き取り確認する」だけでは、既に送られた誤通知を防げません。

### 問3

承認済み契約書を探すため、社員が自由タグだけで文書を管理しています。想定される問題と改善策を説明してください。

**解答例：** 「契約」「契約書」などの表記ゆれ、タグ漏れ、誤った顧客名、承認状態の混在が起こり得ます。文書種別、顧客ID、承認状態などは選択式の統制語彙にし、自由タグは補助に使います。正本の保管場所、版管理、タグの廃止・統合手順も定めます。

**理由：** 探索性はタグだけでなく、正本、版、承認状態を一貫して管理して初めて保てるためです。**不適切な考え方：** 「タグを増やせば解決」は表記ゆれと入力負担を増やします。「ファイル名に全部書く」は更新や検索に弱く、正式な承認状態も保証しません。

### 問4

問い合わせメールをAIが分類し、回答文を生成して自動送信する仕組みを検討しています。識別AI、生成AI、AIエージェントの役割と、段階ごとの統制を説明してください。

**解答例：** 識別AIが問い合わせ種別や緊急度を判定し、生成AIが回答案を作り、AIエージェントが顧客システムの参照や送信を行う構成が考えられます。分類精度と誤判定の影響、参照できる顧客情報、回答根拠、禁止表現、送信権限を確認します。まずは下書きまでに限定して人が確認し、十分な評価後も返金・苦情・個人情報を含む例外は人へ戻し、ログと停止手段を設けます。

**理由：** 分類の誤りが不適切な文章生成を経て、そのまま顧客への実行に連鎖し得るためです。**不適切な考え方：** 「生成文が丁寧なら自動送信できる」は内容の正確さを保証しません。「全権限を与える方が効率的」は誤操作の影響範囲を不必要に広げます。

### 問5

社内規程RAGのモデルと検索索引を同時に更新します。更新前に正答率が高かったことを理由に、そのまま全社反映してよいでしょうか。

**解答例：** そのまま反映せず、モデル版、文書・索引版、プロンプト、権限設定の変更点を記録し、固定した評価質問と重要な例外で変更前後を比較します。正答率だけでなく、旧版引用、権限漏れ、根拠との一致、重要情報の欠落、応答不能時の動作を確認し、合格・停止条件に従って段階反映します。問題時に旧構成へ戻す手順も用意します。

**理由：** モデルと検索対象のどちらも回答へ影響し、同時変更では原因の切分けも難しくなるためです。**不適切な考え方：** 「製品名が同じなので挙動も同じ」は版変更を無視します。「平均正答率だけが維持されればよい」は、少数でも重大な権限漏れや旧規程の引用を見逃します。「利用者から苦情が出たら戻す」は、影響発生後の対応だけに依存し、事前検証と監視を欠きます。

## まとめ

- AI利用では、入力データ、モデル、出力、実行権限、人間の関与を管理する。
- AI出力を根拠なく事実として扱わず、目的と影響に応じて検証する。
- 非構造化データは、保管場所、メタデータ、命名、共有、版管理で探索性と再利用性を保つ。
