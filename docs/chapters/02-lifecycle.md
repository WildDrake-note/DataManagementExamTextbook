# 第2章 データライフサイクル

## 学習目標

- 生成、保管、処理、活用、廃棄の各段階を説明できる。
- 自分の業務データについて、生成元・更新・履歴・削除の流れを確認できる。
- ライフサイクル全体で責任と統制が必要な理由を説明できる。

**シラバス対応**：科目A・重点分野「データライフサイクル」、科目B 1-1、1-3。

> **シラバスの位置付け**：本章が参照するシラバスは Ver.0.1 の「案」です。今後変更される可能性があるため、未公表の試験内容を推測せず、公開済みの「生成、保管、処理、活用、廃棄」と、業務で確認すべき技能に沿って学びます。

## 1. ライフサイクルで考える

データは一度作って終わりではありません。生成され、保管され、処理され、利用され、最終的にアーカイブまたは廃棄されます。途中で複製・共有・加工されるため、元データだけを管理しても不十分です。

ここでいう**ライフサイクル**とは、データが業務の中で生まれてから不要になるまでの一連の流れです。「どのシステムにあるか」という保管場所だけでなく、「何をきっかけに作られ、誰が更新し、何に使われ、いつ消されるか」までを一続きで捉えます。段階は必ず一方向に一度だけ進むとは限りません。例えば、分析で誤りが見つかれば生成時の入力方法を直し、修正されたデータを再処理します。

```text
生成 → 保管 → 処理 → 活用 → アーカイブ／廃棄
  ↑       ↓       ↓       ↓
  └── 品質・権限・メタデータ・履歴を継続管理 ──┘
```

次の図は、受注データを例に、データそのものと管理情報が並行して流れる様子を示します。

```text
[注文確定]
    |
    v
[受注を生成] --> [業務DBに保管] --> [日次集計] --> [売上確認]
    |                  |                 |              |
 入力ルール         権限・バックアップ   変換ルール      利用目的
    |                  |                 |              |
    +------------------+-----------------+--------------+
                           |
                    [保存期限を判定]
                       /       \
              [アーカイブ]   [復元不能に廃棄]
```

各段階を孤立させず、前後のつながりを確認することが重要です。入力が正しくても、集計時に税込金額と税抜金額を混ぜれば結果は誤ります。反対に、集計式だけを直しても、誤った入力が繰り返されるなら根本原因は残ります。

| 段階 | 初学者向けの問い | 主な管理対象 | 放置した場合の例 |
|---|---|---|---|
| 生成 | 何をきっかけに、誰が作るか | 入力規則、必須項目、生成元 | 同じ顧客が表記違いで二重登録される |
| 保管 | 正式な置き場所はどこか | 権限、バックアップ、版、保存期間 | 個人PCの古い表を最新版と誤認する |
| 処理 | どの規則で形を変えるか | 結合・変換・集計の条件、実行履歴 | 単位の違う金額をそのまま合算する |
| 活用 | 誰が何の目的で使うか | 利用目的、対象範囲、鮮度、説明可能性 | 過去時点の在庫で発注を判断する |
| アーカイブ・廃棄 | いつ、何を、誰の承認で残す・消すか | 保存期限、複製、廃棄記録、復元可否 | 不要な個人情報が共有フォルダに残る |

## 2. 各段階の確認事項

### 生成

- 誰が、どの業務イベントで生成するか。
- 入力必須項目、形式、コード体系、発番規則は何か。
- 本人確認や承認は必要か。
- 入力時点で妥当性検証を行えるか。

品質問題は後でクレンジングするより、生成時に予防する方が効率的です。ただし入力制約を過剰にすると業務が回らなくなるため、目的との均衡が必要です。

例えば、営業担当者が新規取引先を登録する場面を考えます。法人番号を利用できる業務なら、それを識別の手掛かりにし、都道府県は自由入力ではなく組織で定めたコードから選択させると、表記ゆれを減らせます。一方、障害対応の受付で詳細がまだ分からないのに全項目を必須にすると、受付自体が遅れます。この場合は「受付時に必要な項目」と「後で補完する項目」を分け、補完期限と担当者を決める方が現実的です。

生成元も確認します。人が画面から入力したデータ、機器が自動送信したログ、取引先から受領したファイルでは、誤りの見つけ方と問い合わせ先が異なるためです。

### 保管

- 正式な保管場所はどこか。
- 暗号化、バックアップ、アクセス権、保存期間は適切か。
- 最新版と過去版を区別できるか。
- 個人端末やメールへ無秩序に複製されていないか。

「正式な保管場所」とは、組織が最新版として管理し、権限やバックアップなどのルールを適用できる場所です。単にファイルが開ける場所という意味ではありません。例えば、月次予算表を共有ストレージで管理していても、担当者がメール添付を更新し続ければ、どれが最新版か分からなくなります。共有ストレージ上の一つを正本とし、メールではリンクを共有する、といった運用で複製を抑えます。

バックアップは障害や誤削除から戻すための複製です。一方、アーカイブは参照頻度が下がったデータを規程に沿って長期保管することです。目的が異なるため、「バックアップがあるからアーカイブは不要」「アーカイブがあるから直近の復旧対策は不要」とは限りません。

### 処理

- 変換、結合、集計のルールは記録されているか。
- 元データから結果まで追跡できるか。
- 加工によって意味・粒度・責任主体が変わるか。
- 失敗時に再実行・復旧できるか。

処理では、**入力データ、処理ルール、出力データ**の三つを対応付けます。例えば、店舗別売上を円単位で集計する前に、海外拠点の売上が現地通貨なら、どの時点の為替レートで換算したかを記録します。結果の数字だけを保存しても、換算日や除外条件がなければ同じ集計を再現できません。

処理途中で一部だけ成功した場合の扱いも重要です。100件中60件を更新して停止した処理を最初から再実行すると、同じ取引を二重計上する設計かもしれません。再実行しても二重反映しない仕組み、処理済み範囲の記録、復旧手順を事前に確認します。

### 活用

- 利用目的と取得時の目的が整合するか。
- 利用者に権限があるか。
- データが十分に新しく、完全で、目的に合うか。
- 分析条件、対象期間、除外条件を説明できるか。

活用では「データが存在する」ことと「その目的に使ってよい」ことを分けて考えます。例えば、配送先住所は商品の配送には必要でも、別の販売促進に利用できるかは、取得時の目的、本人への説明、契約、法令、社内ルールなどの確認が必要です。担当者だけで判断できない場合は、データオーナーや法務・コンプライアンスなど、組織で定められた相談先へ確認します。

また、正しいデータでも時点が違えば判断を誤ります。午前9時時点の在庫一覧を午後5時の緊急発注に使うなら、その間の入出庫が反映されていないことを利用者へ明示する必要があります。

### アーカイブ・廃棄

- 法令、契約、社内規程に沿った保存期間か。
- 業務上不要になった複製も対象に含むか。
- 復元不能な方法が必要か。
- 廃棄の承認と記録を残すか。

「念のため永久保存」は安全策ではありません。漏えい時の影響、保管費用、誤利用、保存義務違反などのリスクを増やします。

アーカイブと廃棄は、利用者個人の感覚ではなく、法令、契約、社内規程、係争や監査上の必要性などに基づいて判断します。廃棄対象には、正式システムのレコードだけでなく、出力したCSV、メール添付、共有フォルダの作業用ファイルなども含めて所在を確認します。ただし、担当者が独断で一括削除してはいけません。保全が必要な記録まで失わないよう、対象、期限、承認者、実施者、実施結果を記録します。

### 一つの業務を端から端まで追う例

架空の修理会社で、顧客から受け付けた修理依頼を考えます。

1. **生成**：受付担当が依頼番号を発番し、製品番号、症状、連絡先を登録する。
2. **保管**：修理管理システムを正本とし、担当者には必要な案件だけを表示する。
3. **処理**：製品番号から製品区分を付与し、症状コード別の件数を日次集計する。自由記述を分類した場合は、その分類規則も残す。
4. **活用**：修理担当は作業計画に、品質管理担当は故障傾向の把握に使う。目的ごとに必要項目と閲覧範囲を変える。
5. **アーカイブ・廃棄**：完了案件を規程に基づいてアーカイブし、期限到来後は承認を経て、作業用出力ファイルを含めて廃棄する。

この例では、受付担当だけが全責任を負うわけではありません。受付担当は入力の正確性、システム管理者は保管と復旧、集計担当は処理条件、利用者は目的と条件の順守、データオーナーはルールや責任分担の確認、といったように役割をつなぎます。異常を見つけた人は、独断で広範囲を書き換えず、影響範囲と証拠を残して所定の責任者へ報告します。

## 3. 識別子、コード、粒度

データの意味を確認する際は、項目名だけでなく次を確認します。

- **識別子**：何を一意に識別するか。全社か部門内か。
- **コード値**：値と表示名の対応、有効期間、廃止値。
- **粒度**：顧客、契約、注文、注文明細など、1行が何を表すか。
- **範囲**：個人顧客を含むか、国内のみかなど。
- **発番規則**：連番か意味のあるコードか。再利用されるか。

異なるシステムで「顧客ID」がどちらも一意でも、各システムの内部でのみ一意なら、そのまま相互結合できません。

例えば、営業システムの顧客ID `1001` が「法人A」を指し、保守システムの顧客ID `1001` が「法人B」を指すことがあります。数字が同じことは、同じ顧客である証拠になりません。どの発番主体のIDかを表すシステム識別子を組み合わせるか、両システムのIDを対応付ける管理済みの変換表を使います。

粒度の違いも結合結果を変えます。注文表が「1行＝1注文」、注文明細表が「1行＝1商品」であるとき、二つを結合すると一つの注文が商品数だけ複数行になります。この結合後に注文金額を単純合計すると、注文金額を重複計上するおそれがあります。結合前に「1行が何を表すか」を言葉で説明できる状態にします。

## 4. 履歴の考え方

上書き更新だけでは「いつ、誰が、なぜ変更したか」を説明できない場合があります。必要に応じて、変更前後の値、変更日時、変更者、根拠を記録します。ただし、すべてのデータに無期限の詳細履歴が必要とは限りません。業務・監査・法令上の必要性で決めます。

履歴には少なくとも二つの目的があります。一つは、誤更新が起きたときに影響を調べたり戻したりする**運用上の目的**です。もう一つは、ある時点で何が登録されていたかを説明する**説明責任の目的**です。例えば、契約の送付先住所を上書きするだけでは、先月送った請求書がどの住所を基に作られたか説明できません。変更前後の住所、有効になった日時、変更理由を必要な期間だけ残せば、当時の処理を追跡できます。

なお、変更履歴を残すことと、バックアップを取ることは同じではありません。履歴は個々の変更を業務上の意味と結び付けて確認するためのものです。バックアップは主に障害などからデータを復旧するためのものなので、変更理由や承認根拠まで分かるとは限りません。

### 業務上の有効時点と記録時点を分ける

遡及訂正を扱う場合は、日付を一つだけ持つと「いつから正しい値か」と「いつ訂正を知ったか」を区別できません。**有効時点**は値が業務上適用される期間、**記録時点**はシステムがその値を保持していた期間です。二つを分けると、当時の報告を再現しながら、訂正後の正しい履歴も計算できます。

| 問い | 固定する有効時点 | 固定する記録時点 | 答えられること |
|---|---|---|---|
| 4月の正しい契約単価は何か | 4月の対象日 | 訂正を含む最新時点 | 後日判明した訂正を含む4月実績 |
| 4月末の担当者は何を知っていたか | 4月末までの対象日 | 4月末時点 | 当時利用できた値による報告・判断の再現 |
| いつ誤りを訂正したか | 訂正対象となる期間 | 記録開始時点 | 訂正の遅れと影響期間 |
| どの帳票を再作成するか | 帳票の対象期間 | 訂正前と訂正後 | 遡及対象と当時確定値の比較 |

```text
業務上の時間:  4/1 ───────────────>  単価1,100円が有効
記録上の時間:  4/1 ── 5/9          単価1,000円として保持
                         5/10 ─────>  訂正を記録

4/30時点の報告を再現  → 1,000円
訂正後に4月実績を再計算→ 1,100円
```

**職場例：契約単価の遡及訂正**

4月1日から1,100円となる契約単価を、誤って1,000円で登録し、5月10日に訂正したとします。4月に12,000個を販売していれば、訂正額は `(1,100－1,000) × 12,000 = 1,200,000円` です。単価を上書きするだけでは、4月末の報告がなぜ1,200,000円少なかったか説明できません。

旧値の有効終了日、新値の有効開始日、訂正を記録した日時、理由、承認、再計算対象を残します。請求や会計の確定後に訂正する場合は、元の帳票を黙って置き換えず、組織の訂正手順に従って差額処理と利用者通知を行います。すべての項目に二時点管理が必要なわけではなく、遡及変更があり、当時状態の説明と訂正後計算の両方が必要なデータへ適用します。

## 5. 自分の業務でライフサイクルを確認する手順

最初から全社のデータを調べるのではなく、自分が日常的に更新するデータを一つ選ぶと取り組みやすくなります。

1. **対象を一文で定義する**：「受注一覧」ではなく「確定した国内法人向け注文を、注文単位で表すデータ」のように、範囲と粒度を書く。
2. **流れを描く**：生成元、正本、加工先、共有先、アーカイブ先、廃棄までを矢印でつなぐ。
3. **担当と根拠を添える**：各段階の実施者、承認者、適用する規程や手順を記入する。
4. **複製と履歴を探す**：CSV出力、メール添付、個人作業ファイル、バックアップなど、主経路以外も確認する。
5. **不明点を相談する**：所在不明、責任者不明、規程との矛盾を記録し、データオーナーやデータ主管組織など所定の窓口に相談する。

この手順の成果物は、立派なシステム図でなくても構いません。データ名、段階、場所、担当、保存期間、不明点を表にするだけでも、削除漏れや属人化を見つける手掛かりになります。

## 6. 引き渡しから削除確認までを切れ目なく管理する

ライフサイクル上の事故は、一つの処理の内部だけでなく、担当者・部門・組織・システムの**引き渡し点**で起きやすくなります。送信側は「渡したので完了」、受信側は「正しいものが届いたはず」と考えると、件数不足、形式変更、二重取込み、権限の引継ぎ漏れが見逃されます。引き渡しでは、データ本体だけでなく、その意味と取扱条件も渡します。

| 引き渡す情報 | 確認内容 | 受信側の検証例 | 欠けた場合のリスク |
|---|---|---|---|
| 対象と基準時刻 | 何の、いつ時点のデータか | 対象期間と抽出時刻を照合する | 新旧データを混在させる |
| 件数・完全性 | 期待件数、必須項目、分割単位 | 件数、欠損、連番の抜けを確認する | 一部欠落を正常処理と誤認する |
| 意味・形式 | 定義、単位、コード、文字コード | スキーマとコード版を検証する | 円と千円、予定と実績を混同する |
| 取扱条件 | 目的、権限、保存期限、再提供可否 | 受信先権限と期限設定を確認する | 許可のない再利用や長期保管が起きる |
| 処理結果 | 成功・失敗件数、再実行単位 | 送受信の件数と制御合計を突合する | 一部成功後の再実行で二重登録する |
| 問合せ・訂正 | 責任者、訂正通知、再配布方法 | エラー時の連絡先を試験する | 誤り判明後も派生先に残る |

### 正本から増えるコピーを追跡する

データは、API連携、分析基盤、CSV、メール添付、キャッシュ、端末へのダウンロード、バックアップなどへ広がります。すべてのコピーを禁止するのではなく、業務上必要なコピーについて、**正本との関係、所有者、作成目的、更新方法、保存期限、削除方法**を把握します。特に、コピーからさらに作られた派生データは見落とされやすいため、訂正と削除の通知先をたどれるようにします。

```text
                        [バックアップ]
                              |
                              v
[正本] --API--> [業務システム] --出力--> [作業CSV] --> [メール添付]
  |                 |                       |
  |                 +--> [集計表]           +--> [個人端末]
  |                          |
  +---- 訂正・保留・期限の通知 +-----------> 各保有先
                             |
                             v
                     [削除結果を回収・照合]

「正本を削除した」だけでは、右側のコピーや復元可能なバックアップに
同じデータが残っている可能性がある。
```

バックアップは通常、個別レコードを即時に取り除く用途には向きません。その場合も放置するのではなく、バックアップの世代期限、アクセス制限、復元時に削除対象を再削除する手順など、組織の規程と技術上の特性に沿った統制を決めます。削除方法は媒体やサービスによって異なるため、「削除キーを押した」という操作だけで復元不能と断定しません。

### 保存期間、法的保全、アーカイブの優先関係

保存期間は、「作成から5年」のような年数だけでは不十分です。何を起点に数えるか、どの版を対象とするか、期限後に自動削除するか、例外を誰が承認するかまで定めます。法令、契約、業務、監査など複数の根拠がある場合は、所定の責任者が矛盾を整理します。

係争、調査、監査などに関連するデータについて、通常の削除を一時停止して保全する措置をここでは**法的保全（リーガルホールド）**と呼びます。対象通知を受けたら、通常の保存期限が来ても独断で削除しません。一方、「関係するかもしれない」という理由で全社データを永久保存するのも不適切です。対象者、期間、データ種類、保有場所を可能な範囲で特定し、解除の正式通知後に通常ルールへ戻します。具体的な法的判断は、組織の法務部門など所定の責任者へ確認します。

| 状態 | 主な目的 | 典型的な操作 | 終了の判断 |
|---|---|---|---|
| 通常保管 | 現行業務で利用する | 更新可能な状態で権限管理する | 業務完了や規程上の移行条件 |
| アーカイブ | 低頻度参照・証跡のため保持する | 改変を抑え、検索・取出し可能にする | 保存期限または再評価日への到達 |
| 法的保全 | 係争・調査等に必要な証拠を保つ | 通常削除を停止し、対象と通知を記録する | 権限ある部門からの解除通知 |
| 廃棄 | 不要データと残存リスクをなくす | 承認後、媒体に適した方法で削除する | 実施結果と例外の照合完了 |

法的保全は新しい保存期間を恒久的に付けるものではありません。保全が解除されたら、元の期限が未到来なら残期間を管理し、すでに期限を過ぎているなら承認済みの廃棄手続へ進めます。アーカイブも「何でも残す倉庫」ではなく、検索性、真正性、アクセス制限、取出し試験、廃棄予定を維持する管理対象です。

### 削除は実行ではなく検証で完了する

削除作業の完了条件を、「コマンドが成功した」だけにしてはいけません。対象一覧と実施結果を突き合わせ、失敗、対象外、保全中、技術上すぐ消せないコピーを例外として記録します。一般的には次の順序で確認します。

1. 対象、根拠、期限、保全の有無、承認者を確定する。
2. 正本、連携先、作業コピー、派生物、バックアップ方針を対象一覧にする。
3. 業務停止や証拠破壊を避けるため、実行方法と復旧影響をレビューする。
4. 承認済みの方法で削除し、対象件数、成功件数、失敗件数を記録する。
5. 再検索、再取得試験、権限確認など、対象に適した方法で残存を確認する。
6. 失敗と例外を是正し、承認者が結果を確認して記録を閉じる。

ここでいう検証は、データの内容を廃棄記録へ丸ごと複写することではありません。廃棄記録自体が新たな機密データにならないよう、対象を特定できる管理番号、根拠、件数、日時、方法、実施者、承認者、例外など必要最小限を残します。

#### 発展的な業務例：キャンペーン終了後の応募者データ

小売会社が抽選キャンペーンを実施し、応募フォームから氏名、連絡先、購入証明を収集しました。フォームの正本はキャンペーン管理システムですが、抽選委託会社へ暗号化ファイルを渡し、社内担当者も問い合わせ対応用CSVを共有フォルダへ出力しています。集計担当は個人を識別しない地域別応募件数を分析基盤に作りました。

終了時、担当者は正本だけを削除するのではなく、データフローと受渡記録から保有先を一覧化しました。ところが、当選結果に関する紛争が発生し、法務部門から特定期間・特定応募分の法的保全通知が届きました。担当者は対象分の通常削除を止め、アクセスを限定した保全領域へ移し、対象外の応募者データは規程どおり削除しました。委託会社には契約上の削除を依頼し、完了証跡を受領しました。共有CSVは削除後に同じ保存先とファイル識別情報で残存確認を行いました。

分析基盤の地域別件数は個人へ戻せるか、元応募データの削除要求と連動すべきかをデータオーナーと確認しました。十分に集計され個人と結び付かないと確認できたため、統計として別の保存ルールを適用しました。後日、法務部門が保全解除を通知すると、保全対象にも通常の期限判定を再適用し、期限超過分を承認後に廃棄しました。この例の要点は、**一律に全部残す・全部消すのではなく、コピー、派生物、保全対象、検証証跡を区別したこと**です。

## 7. イベントを起点にコピーと保存期限を統制する

ライフサイクルを実際に動かすには、「5年保存」のような静的な一覧だけでなく、契約終了、退職、同意撤回、訂正、法的保全、システム廃止などの**イベント**を検知し、必要な処理を開始する仕組みが必要です。以下はシラバス案の出題範囲を推測するものではなく、公開済みのライフサイクル概念を職場の統制へ落とす実践例です。

イベントごとに、誰が通知し、どのデータを識別し、どの期限で、どの保有先へ何を行い、結果を誰が確認するかを決めます。通知メールだけに頼ると、担当者の不在やコピーの見落としで処理が止まります。

| イベント | 主な統制動作 | 完了を示す証拠 | 代表的な例外 |
|---|---|---|---|
| 契約終了 | 利用停止、アーカイブ・期限判定を開始 | 権限無効化記録、対象台帳 | 未精算取引が残る |
| 訂正・削除確定 | 正本を処理し派生先へ通知 | 通知先と処理結果の照合 | バックアップは世代期限まで隔離 |
| 法的保全の開始 | 通常削除を停止し対象を固定 | 保全通知、範囲、保有場所 | 通知対象外は通常処理を継続 |
| 法的保全の解除 | 元の期限を再計算して処理を再開 | 解除通知、再判定結果 | 別の保全根拠が継続中 |
| システム廃止 | 移行、不要コピー削除、接続停止 | 移行件数、残存確認、承認 | 監査用アーカイブが必要 |

### コピー台帳を通知と照合の経路にする

第6節のデータフロー図を、実行可能な**コピー台帳**へ落とします。コピーごとに、データ集合、所在、正本との関係、所有者、作成方法、更新方法、保存根拠、期限起点、削除方法、下流の通知先を記録します。個々の値を台帳へ複写するのではなく、保有先と処理責任を追える粒度にします。

```text
[契約終了イベント]
          |
          v
[対象ID・期限・保全を判定] ---> [コピー台帳から処理先を展開]
          |                          /       |        \
          |                       [正本]  [分析先]  [委託先]
          |                          |       |         |
          +---- 例外台帳 <-----------+-------+---------+
                          処理結果・件数
                                  |
                                  v
                    [期待対象と実績を照合・承認]
```

新しい出力や連携を作るときに台帳へ登録し、所有者不明、期限不明、削除方法未確認のコピーは是正対象にします。台帳が古くならないよう、アクセス権レビュー、連携変更、システム棚卸しなど既存の業務イベントと更新を結び付けます。

### 保存根拠が競合したら勝手に長い方・短い方を選ばない

一つのデータに法令、契約、業務、監査、法的保全の複数条件がかかることがあります。担当者が単純に最長期間を選ぶと、契約上の削除約束やデータ最小化に反する場合があります。最短期間を選べば保存義務や証拠保全に反するおそれがあります。

まず、対象範囲、期限の起点、終了条件、適用地域、正本とコピーへの適用を根拠ごとに記録します。次に、矛盾をデータオーナー、法務、記録管理、セキュリティなど組織所定の責任者へ上げ、決定理由、承認者、見直し日を残します。法的保全は通常期限を一時停止しますが、解除後は元の期限を再判定します。技術上すぐ削除できない場合は、アクセス停止、隔離、世代期限での消去など代替統制と解消期限を承認します。

### 件数照合は例外をゼロに見せず閉じる

処理後は、「期待対象件数 ＝ 成功件数 ＋ 失敗件数 ＋ 承認済み例外件数」という制御合計を、コピー台帳の各保有先で確認します。単に成功件数だけを見ると、そもそも処理対象へ展開されなかったコピーを発見できません。件数に加え、対象IDの突合、再検索、権限停止、委託先証跡など、場所に合った確認を行います。

失敗と例外には、理由、所有者、次回処理日、代替統制、承認者を付けます。翌日の再実行後は前日の数字を上書きせず、どの例外が解消し、何が残ったかを履歴で追います。照合差異がゼロ、または残る例外が正式承認されるまで、イベントを完了扱いにしません。

#### 実務例：法人顧客の契約終了

あるクラウドサービス会社では、契約管理システムで法人顧客の解約が確定すると、利用アカウント停止とデータ処理の案件が自動起票されます。対象IDをキーにコピー台帳を検索すると、正本、請求システム、分析基盤、サポートCSV、バックアップ、運用委託先が見つかりました。

契約には終了後30日で顧客入力データを削除する条件があり、会計証憑には別の保存義務がありました。さらに未解決の請求紛争について法的保全が通知されていました。担当者は全部を一律に残さず、顧客入力データ、会計証憑、保全対象を分類し、所定の責任者が根拠と期限を承認しました。保全対象は隔離してアクセスを限定し、対象外のサポートCSVと委託先コピーは期限どおり処理しました。

最後に保有先ごとの期待件数と、成功・失敗・例外件数を照合しました。バックアップ分は即時削除できない承認済み例外として、世代期限、復元時の再削除手順、担当者を記録しました。委託先の処理証跡も回収し、1件の失敗を再実行してから案件を閉じました。これにより、**イベント検知、コピー台帳、根拠の競合解決、結果照合**が一つの統制としてつながります。

## 8. 保存スケジュールをレコードへ適用する

保存方針に「取引データは5年」のような一行があっても、実際のレコードをいつアーカイブし、いつ廃棄するかは決まりません。保存スケジュールには、**対象となるレコード群、期限の起点、保存根拠、処分方法、例外、確認責任者**を含めます。年数は法令だけでなく、契約、業務、監査、係争など複数の事情で決まるため、担当者が一般例をそのまま当てはめず、組織の規程と所定の専門部門へ確認します。

| 設計項目 | 決める内容 | 失敗例 |
|---|---|---|
| レコード分類 | 請求書、作業ログ、問い合わせ記録など意味で分ける | 同じストレージ内をすべて同一期限にする |
| 起点イベント | 契約終了、最終取引、案件完了など | 作成日だけを使い、案件中に期限が来る |
| 根拠と適用範囲 | どのデータ、地域、期間、版に何が適用されるか | 根拠名だけ残し、対象範囲を説明できない |
| 処分 | 廃棄、アーカイブ、再評価のどれか | 期限到来後も自動的に保存を続ける |
| 例外 | 法的保全、未精算、技術的制約と解除条件 | 例外に終了日や責任者がない |
| 検証 | 対象抽出、処理結果、残存確認、承認 | ジョブ成功を全件廃棄の証拠とみなす |

保存期間は保管場所ではなく、レコードの業務上の意味に割り当てます。同じ顧客フォルダでも、請求証憑、日常連絡、障害調査記録で根拠や起点が異なる場合があります。反対に、同じ請求証憑が正本、検索用コピー、委託先に分かれていても、同じ分類と処分判断を追跡できなければなりません。

```text
[業務イベント]
      |
      v
[対象IDを確定] --> [レコード分類] --> [起点・根拠・例外を評価]
                                             |
                         +-------------------+------------------+
                         v                   v                  v
                    [通常保管]         [アーカイブ]       [廃棄候補]
                                                                 |
                         [法的保全など] --該当--> [処理を保留・再評価日]
                                                                 |
                                                    [実施・残存確認・承認]
```

### 職場例：案件終了フォルダを一括削除しない

保守会社で一つの大型案件が終了し、関連する18,000件を処理することになりました。内訳を確認すると、請求・契約関係が12,000件、設備の一時作業ログが5,500件、継続中の紛争に関係する記録が500件で、合計は `12,000＋5,500＋500 = 18,000件` でした。フォルダ単位で一括削除すると、必要な証拠を失う一方、すべてを残せば不要な作業ログまで保有し続けます。

担当者は、まず案件IDと文書種別で分類し、請求・契約関係には承認済みの保存スケジュールを適用しました。一時作業ログは、他案件の障害分析に必要なものが混ざっていないかをオーナーが確認してから廃棄候補にしました。紛争関連500件は法務部門の通知範囲と照合し、通常削除を停止してアクセスを限定しました。分類不能なレコードは推測で削除せず、所有者と判断期限を付けた例外にしました。

処理後は、分類ごとの期待件数と成功・失敗・保留件数を照合し、検索用コピーと委託先も確認します。合計件数が一致しても、誤分類があれば必要記録を消すおそれがあるため、件数照合に加えて代表レコードの分類根拠も点検します。保存スケジュールの目的は、一括して長く残すことでも早く消すことでもなく、各レコードを根拠ある次の状態へ移すことです。

## 確認問題（本書オリジナル）

以下の4問は、いずれも本書独自の問題です。

### 問1：複製先を含む廃棄

退職者の連絡先一覧を、人事システムでは規程どおり削除しました。しかし複数部門が表計算ファイルへ複製していました。ライフサイクル管理上の問題は何ですか。

**解答例：** 正式システムだけを削除対象とし、複製先を把握・統制できていません。データの所在、共有履歴、保存期間、廃棄責任をライフサイクル全体で管理する必要があります。理由は、同じ内容が表計算ファイルに残っていれば、元システムから消しても漏えいや目的外利用のリスクが残るからです。

**よくある誤答と不適切な理由：** 「人事システムで削除済みなので問題ない」は不適切です。ライフサイクルの対象は正本だけではなく、業務で生じた複製や共有先にも及びます。各部門に無条件で即時削除を命じるだけの対応も、保存義務や係争上の保全が必要なファイルまで消すおそれがあるため、対象と根拠を確認して所定の手続で廃棄します。

### 問2：集計誤りの根本原因

月次売上が実態より大きいことが分かりました。調べると、「1行＝1注文」の注文表と「1行＝1商品」の注文明細表を結合した後、各行に繰り返し表示された注文金額を合計していました。まず行う対応と、恒久対応を説明してください。

**解答例：** まず誤った集計結果の利用を止め、対象期間、利用先、意思決定への影響を確認し、関係者へ報告します。修正した条件で再集計するのは暫定対応です。恒久対応では、注文表と注文明細表の粒度、キー、一対多の関係を定義として明示し、注文単位で先に集計する、または明細金額を合計するなど目的に合った処理へ直します。さらに、処理ルールのレビューや合計値の照合を組み込みます。これは、表示された数字だけでなく、粒度の不一致という根本原因を取り除くためです。

**よくある誤答と不適切な理由：** 「大きすぎる分を担当者が表計算で差し引く」だけでは不十分です。今回の数字は直せても、同じ結合を翌月実行すれば再発し、手修正の根拠も追跡しにくくなります。また、原因調査前に元データを削除すると、影響範囲の確認や正しい再集計ができなくなります。

### 問3：古い在庫データの活用

発注担当者が、午前9時に出力した在庫CSVを午後5時に使って追加発注しようとしています。その間にも入出庫があります。担当者はどのように判断・行動すべきですか。

**解答例：** まずCSVの基準時刻、午後5時までの更新有無、正本となるシステム、追加発注に必要な鮮度を確認します。可能なら正本から最新値を取得し、取得できない場合は未反映分と業務影響を整理して、上長やデータオーナーなど所定の責任者に判断を仰ぎます。理由は、午前9時時点では正確だったデータも、午後5時の発注判断には最新性が不足する可能性があるからです。利用した時点と条件も記録します。

**よくある誤答と不適切な理由：** 「正式なシステムから出力したCSVなので、そのまま使える」は不適切です。生成元が信頼できても、複製後は自動更新されず、時間経過によって目的適合性が失われます。反対に「古い可能性があるので全商品を多めに発注する」対応も、欠品を避ける代わりに在庫過多を招き、データの確認を省略しているため根拠ある判断になりません。

### 問4：保存期限と法的保全

保存期限を迎えた苦情対応記録を自動削除する予定でしたが、法務部門から、係争に関係する特定顧客・特定期間の記録を保全するよう正式な通知が届きました。最も適切な対応はどれですか。

1. 保存期限が規程にあるため、通知対象も予定どおり削除する。
2. 念のため、全顧客の全記録を永久に保存する。
3. 通知で特定された範囲の通常削除を停止し、正本と関連コピーを保全・記録する。対象外は通常ルールを適用し、解除通知後は期限を再判定する。
4. 担当者のPCに対象ファイルをコピーしてから、正式システムでは削除する。

**解答：3。** 法的保全中の対象は通常の削除から除外し、所在、範囲、アクセス、通知を管理します。同時に、対象外まで無期限保存しないこと、解除後に通常のライフサイクルへ戻すことが重要です。

**よくある誤答と不適切な理由：** 1は正式な保全通知を無視し、必要な証拠を失うおそれがあります。2は対象範囲と終了条件を欠き、漏えい・費用・不要保有のリスクを増やします。4は管理外コピーを増やすだけで、真正性、権限、解除後の削除を統制できません。保全は個人の退避作業ではなく、承認された場所と手順で実施します。

## まとめ

- ライフサイクルは生成から廃棄までを一体として扱う。
- 加工・複製・共有によってデータの意味、品質、責任、リスクが変化する。
- 定義、識別子、粒度、範囲、履歴を確認してから利用する。
- 引き渡しでは、データ本体とともに基準時刻、完全性、意味、利用条件、訂正方法を確認する。
- 保存期限と法的保全を区別し、解除後は通常の期限判定へ戻す。
- 廃棄は正本だけでなくコピーと派生先を対象にし、実施結果と残存確認を照合して完了する。
- 契約終了などのイベントを起点に、コピー台帳、保存根拠の競合解決、件数照合を一続きで管理する。
- 遡及訂正では、業務上の有効時点とシステムへの記録時点を分け、当時状態と訂正後状態を再現する。
- 保存スケジュールは、レコード分類、期限の起点、根拠、処分、例外、検証を結び付け、保管場所単位の一括判断を避ける。
