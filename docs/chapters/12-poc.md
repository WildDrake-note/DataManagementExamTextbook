# 第12章 技術動向とPoC

## 学習目標

- 新技術の情報を複数の情報源から収集し、信頼性と業務適合性の観点で評価できる。
- 技術の特徴、期待効果、制約を整理し、PoCの対象ユースケースを選べる。
- 関係者と調整し、PoCの課題、仮説、成功条件、対象データ、日程を定義できる。
- 定量・定性の両面から検証結果、有効性、課題、費用対効果を整理できる。
- 本格導入、追加検証、保留、中止の判断材料を関係者へ提案できる。

**シラバス対応**：科目B 4-1～4-3。

## 1. 技術動向を把握する目的

新技術を追う目的は、流行に乗ることではなく、自組織の課題へ適用できる選択肢を増やすことです。「何が新しいか」だけでなく、「何が実現でき、どの条件では使えないか」を把握します。

```text
国内外の動向・事例
        ↓
できること／できないことを整理
        ↓
自組織の課題・データ・制約と照合
        ↓
候補ユースケースを比較
        ↓
不確実性が大きく、検証価値があるものをPoCへ
```

### 情報源の使い分け

| 情報源 | 確認しやすい内容 | 注意点 |
|---|---|---|
| 法令・規制当局・政府機関 | 遵守事項、政策、リスク | 公開時点と適用範囲を確認する |
| 標準化団体・技術仕様 | 共通仕様、相互運用性 | 実装が仕様どおりとは限らない |
| ベンダー公式仕様 | 機能、契約、動作条件 | 宣伝表現と保証範囲を分ける |
| 査読論文・実証報告 | 方法、評価条件、限界 | 自組織とデータ条件が異なる |
| 導入事例 | 業務効果、運用上の工夫 | 成功例が選択されている可能性がある |
| 専門家・コミュニティ | 実務上の問題、更新情報 | 発信者、根拠、再現性を確認する |

一つの記事だけで判断せず、一次情報と実務事例を組み合わせます。公開日、対象バージョン、評価データ、比較対象、スポンサーの有無も確認します。

### 職場例：生成AIによる社内検索

担当者が「他社で回答時間を50%短縮」という事例を見つけても、その数値を自社へそのまま適用できません。対象文書の種類、文書整備状況、質問の難易度、正答の定義、人による確認時間、利用製品の版を確認します。自社文書に古い版やアクセス制限の異なる文書が混在するなら、検索精度より先に文書管理が課題になることもあります。

## 2. 適用可能性とユースケースの選定

技術ありきで用途を探すと、「試せたが業務価値がないPoC」になりがちです。課題と期待効果から候補を比較します。

| 観点 | 確認する問い |
|---|---|
| 業務課題 | 現在、誰が、どの場面で困っているか |
| 基準値 | 時間、費用、誤り、品質の現状はいくつか |
| 技術適合性 | 技術が直接改善できる部分はどこか |
| 必要データ | 量、品質、利用許可、正解データはあるか |
| 利用者・運用者 | 誰が使い、確認し、保守するか |
| リスク | セキュリティ、法務、倫理、誤作動の影響は何か |
| 連携 | 既存システムとどのように入出力するか |
| 経済性 | 導入・運用費用に見合う効果があり得るか |
| 撤退可能性 | 停止、データ返却、代替手段を確保できるか |

### 候補ユースケースの比較例

| 候補 | 課題の大きさ | データ準備 | 誤りの影響 | PoC向きか |
|---|---|---|---|---|
| FAQ回答候補の提示 | 中 | 過去FAQがある | 人が確認可能 | 高い |
| 融資の自動承認 | 大 | 履歴あり | 顧客への影響が重大 | 初回PoCでは慎重 |
| 会議室利用の予測 | 小 | 予約ログあり | 小さい | 技術確認には適するが価値を要確認 |

PoC対象は、課題が重要であるだけでなく、限定条件で検証でき、結果から次の判断ができることが重要です。

## 3. PoCとは何か

PoC（Proof of Concept）は、限定された条件で「考え方や技術が有効か」を検証する取組です。完成品を作ることや、本番導入を既定路線にすることではありません。

| PoC | 本番導入 |
|---|---|
| 主要な不確実性を検証する | 継続的に業務価値を提供する |
| 対象・期間・データを限定できる | 全対象と例外を安定して扱う |
| 手作業を一部許容する場合がある | 運用、監視、障害対応が必要 |
| 不成立も有益な結論 | サービス水準と責任を負う |

良いPoCは成功を演出するものではなく、「導入」「追加検証」「保留」「中止」を区別できる証拠を集めます。

## 4. PoCを企画する

### 4.1 課題・仮説・成功条件

課題は現状の困り事、仮説は技術によって起こせる変化、成功条件はその仮説を採用できる基準です。

```text
課題：問い合わせ分類に時間がかかる
  ↓
仮説：分類AIで一次分類時間を30%短縮できる
  ↓
成功条件：時間、精度、重大見逃し、確認負荷、情報管理
  ↓
検証条件：対象、期間、比較方法、評価者、データ版
```

成功条件は一つの精度指標だけにしません。

| 区分 | 成功条件の例 |
|---|---|
| 業務効果 | 1件当たり一次分類時間を30%短縮する |
| 品質 | 業務上必要な分類精度を満たす |
| 重大リスク | 緊急案件の見逃し率を許容範囲内にする |
| 利用者負荷 | 確認・修正時間を含めても総時間が短縮する |
| 技術 | 想定件数を制限時間内に処理する |
| 統制 | 機密情報を規程と契約に従って扱える |
| 経済性 | 想定利用量で便益が運用費を上回る見込みがある |

### 4.2 検証条件を固定する

対象、期間、サンプル数、比較方法、評価者、データ版、除外条件を事前に定めます。結果を見た後で成功条件や除外条件を変えると、都合のよい事例だけが残り、検証の信頼性が下がります。変更が必要なら、理由と影響を記録し、探索的な結果と正式評価を分けます。

### 4.3 役割とスケジュール

| 役割 | 主な責任 |
|---|---|
| 業務責任者 | 課題、成功条件、導入判断 |
| 業務担当者 | 現行手順、例外、利用者評価 |
| データオーナー | データ利用の承認、条件確認 |
| データ主管組織・分析担当 | データ、評価設計、結果の妥当性 |
| IT部門 | 環境、連携、アクセス、運用評価 |
| 法務・セキュリティ | 契約、法令、リスク対策 |
| PoC責任者 | 日程、課題、変更、結果の統合 |

日程には、準備、データ確認、実施、評価、結果説明、データ廃棄まで含めます。

## 5. 事前準備と調整

PoCだから統制を省略してよいわけではありません。限定環境や疑似データを用いることで、検証目的を保ちながらリスクを抑えます。

### 事前チェック表

- データオーナーと試行的利用の許可
- 個人情報・機密情報・契約上の利用条件
- 社内IT環境、アカウント、アクセス権
- 外部サービスの保存場所、再学習利用、再委託、削除条件
- データ抽出、マスキング、匿名化、保管、廃棄
- 対象データの定義、品質、版、正解データ
- 実施体制、問い合わせ先、最終承認者
- 事故時の停止、報告、復旧手順
- 費用上限、利用量上限、終了条件

### 職場例：外部AIサービスのPoC

購買部が契約書要約を試す場合、実契約書を個人アカウントから入力してはいけません。データオーナー、法務、IT部門と、入力可能な文書、サービス側の保存・学習条件、アクセス権、出力の確認者、終了後の削除を調整します。目的が操作性の確認なら、まず架空契約書で試す選択肢もあります。

## 6. 実施と評価

実施中は、成功例だけでなく入力、処理、出力、例外、設定変更を記録します。

```text
計画した条件
   ↓
実施 ──→ 例外・変更を記録
   ↓
結果を成功条件ごとに比較
   ↓
失敗例と原因候補を分析
   ↓
本番との差・未確認事項を整理
```

| 評価領域 | 定量例 | 定性例 |
|---|---|---|
| 業務効果 | 時間短縮率、処理件数 | 作業の分かりやすさ |
| 品質 | 正答率、見逃し率、修正率 | 誤りの重大性、説明の納得感 |
| 運用 | 障害件数、確認時間 | 例外処理の難しさ |
| 技術 | 応答時間、可用性 | 既存画面との使い勝手 |
| 経済性 | 1件当たり費用、削減工数 | 費用仮定の確からしさ |

精度が高くても、本番データを継続取得できない、処理時間が長い、説明責任を満たせないなら導入不適合かもしれません。平均精度だけでなく、重大な失敗がどの条件で起きたかを確認します。

### 費用対効果の捉え方

```text
期待便益
  ＝ 削減時間 × 対象件数 × 人件費換算
    ＋ 品質向上・機会損失低減など

総費用
  ＝ 初期費用 ＋ 利用料 ＋ 連携・運用・監視・教育・確認の費用
```

仮定を明示し、過大な便益や見落とした運用費がないかを確認します。PoC時の無料枠や手作業支援を、本番費用の見積りから除外し忘れないようにします。

## 7. 本番との差を評価する

| 項目 | PoCで起こりやすい状態 | 本番で確認すべきこと |
|---|---|---|
| データ量 | 少量・選別済み | 全量、繁忙時、未知の入力 |
| データ品質 | 整備済み | 欠損、表記揺れ、遅延 |
| 利用者 | 協力的な少人数 | 習熟度の異なる全利用者 |
| 運用 | 専門家が随時支援 | 問合せ、監視、障害、変更管理 |
| 連携 | 手作業で入出力 | 認証、API、性能、再処理 |
| 費用 | 無料枠・短期間 | 継続利用、保守、教育、監査 |

小規模データで成功したことは、全社規模での性能・品質・運用を保証しません。差が大きい項目は、本格導入前の追加検証又は対策として明示します。

## 8. 結果を共有し、提案する

結果報告は、技術デモではなく意思決定資料です。

1. 検証目的、仮説、対象ユースケース
2. 対象データ、期間、比較方法、変更点
3. 成功条件と実績の比較
4. 確認できた業務効果と有効性
5. 失敗例、未確認事項、限界
6. 業務・技術・法務・運用上の課題と対策
7. 本番化に必要な体制、費用、日程
8. PoC環境と本番環境の差
9. 導入、追加検証、保留、中止の提案と理由

### 判断の分岐

```text
成功条件を満たしたか
  ├─ はい ─→ 本番との差と残存リスクは許容可能か
  │             ├─ はい → 導入計画を提案
  │             └─ いいえ → 対策又は追加検証
  └─ いいえ → 改善可能で、追加検証の価値があるか
                ├─ はい → 条件を見直して追加検証
                └─ いいえ → 保留又は中止
```

不成立という結果も、理由と条件を記録すれば組織のノウハウになります。同じ技術を別部門が重複して試すことを防ぎ、条件が変わったときの再検討材料にもなります。

## 確認問題（本書オリジナル）

### 問1

生成AIによる文書要約PoCで、担当者が選んだ短い文書10件すべてを正しく要約できました。本番導入判断に不足する情報を挙げてください。

**解答例：** 対象選定の偏り、長文・表・画像・例外文書、評価基準、複数評価者の一致、誤要約の影響、機密性、処理時間、費用、利用者の確認負荷、本番規模、モデル変更時の再評価が不足しています。少数の選別済み文書では本番条件を代表しないためです。「10件全て成功したので導入する」のは標本の偏りと運用リスクを無視するため不適切です。「1件でも将来誤る可能性があるので中止する」のも、誤りの影響と人による確認などの対策を評価していないため不適切です。

### 問2

問い合わせ分類AIのPoCで分類精度は目標を達成しましたが、担当者の確認時間を含めると総作業時間が10%増えました。どのように提案しますか。

**解答例：** 業務効果の成功条件は未達と整理し、確認が増えた分類や画面操作を分析します。改善見込みと追加検証費用が妥当なら対象分類を限定して再検証し、見込みが乏しければ保留又は中止を提案します。技術精度と業務効果は別だからです。「精度を達成したので全面導入」は現場負荷を無視するため不適切です。「時間が増えたので直ちに技術全体を否定する」のも、限定適用や操作改善の可能性を調べていないため不適切です。

### 問3

ベンダー事例では需要予測により在庫を30%削減できたと説明されています。PoC候補にする前に何を確認しますか。

**解答例：** 事例の業種、商品特性、基準値、比較期間、需要変動、対象データ、削減と欠品の関係、利用した版、導入・運用費、自社データの取得可能性を確認します。事例の適用条件が自社と同じとは限らないためです。「著名企業の事例なので同じ効果を見込む」のは条件差を無視するため不適切です。「ベンダー情報は宣伝なので全て無視する」のも、公式仕様や検証条件を知る情報源まで捨てるため不適切です。

## まとめ

- 技術動向は複数の情報源から収集し、自組織の課題、条件、リスクに照らして評価する。
- PoC対象は、業務価値があり、限定条件で主要な不確実性を検証できるユースケースから選ぶ。
- 課題、仮説、成功・中止条件、対象データ、役割、日程を実施前に定める。
- 結果は精度だけでなく、業務効果、品質、運用、リスク、費用対効果で評価する。
- 限界、本番との差、必要な体制・費用・日程を示し、導入、追加検証、保留、中止を提案する。
