# 第12章 技術動向とPoC

## 学習目標

- 新技術の情報を複数の情報源から収集し、信頼性と業務適合性の観点で評価できる。
- 技術の特徴、期待効果、制約を整理し、PoCの対象ユースケースを選べる。
- 関係者と調整し、PoCの課題、仮説、成功条件、対象データ、日程を定義できる。
- 定量・定性の両面から検証結果、有効性、課題、費用対効果を整理できる。
- 本格導入、追加検証、保留、中止の判断材料を関係者へ提案できる。

**シラバス対応**：科目B 4-1～4-3。

## 1. 技術動向を把握する目的

新技術を追う目的は、流行に乗ることではなく、自組織の課題へ適用できる選択肢を増やすことです。「何が新しいか」だけでなく、「何が実現でき、どの条件では使えないか」を把握します。

```text
国内外の動向・事例
        ↓
できること／できないことを整理
        ↓
自組織の課題・データ・制約と照合
        ↓
候補ユースケースを比較
        ↓
不確実性が大きく、検証価値があるものをPoCへ
```

### 情報源の使い分け

| 情報源 | 確認しやすい内容 | 注意点 |
|---|---|---|
| 法令・規制当局・政府機関 | 遵守事項、政策、リスク | 公開時点と適用範囲を確認する |
| 標準化団体・技術仕様 | 共通仕様、相互運用性 | 実装が仕様どおりとは限らない |
| ベンダー公式仕様 | 機能、契約、動作条件 | 宣伝表現と保証範囲を分ける |
| 査読論文・実証報告 | 方法、評価条件、限界 | 自組織とデータ条件が異なる |
| 導入事例 | 業務効果、運用上の工夫 | 成功例が選択されている可能性がある |
| 専門家・コミュニティ | 実務上の問題、更新情報 | 発信者、根拠、再現性を確認する |

一つの記事だけで判断せず、一次情報と実務事例を組み合わせます。公開日、対象バージョン、評価データ、比較対象、スポンサーの有無も確認します。

### 職場例：生成AIによる社内検索

担当者が「他社で回答時間を50%短縮」という事例を見つけても、その数値を自社へそのまま適用できません。対象文書の種類、文書整備状況、質問の難易度、正答の定義、人による確認時間、利用製品の版を確認します。自社文書に古い版やアクセス制限の異なる文書が混在するなら、検索精度より先に文書管理が課題になることもあります。

## 2. 適用可能性とユースケースの選定

技術ありきで用途を探すと、「試せたが業務価値がないPoC」になりがちです。課題と期待効果から候補を比較します。

| 観点 | 確認する問い |
|---|---|
| 業務課題 | 現在、誰が、どの場面で困っているか |
| 基準値 | 時間、費用、誤り、品質の現状はいくつか |
| 技術適合性 | 技術が直接改善できる部分はどこか |
| 必要データ | 量、品質、利用許可、正解データはあるか |
| 利用者・運用者 | 誰が使い、確認し、保守するか |
| リスク | セキュリティ、法務、倫理、誤作動の影響は何か |
| 連携 | 既存システムとどのように入出力するか |
| 経済性 | 導入・運用費用に見合う効果があり得るか |
| 撤退可能性 | 停止、データ返却、代替手段を確保できるか |

### 候補ユースケースの比較例

| 候補 | 課題の大きさ | データ準備 | 誤りの影響 | PoC向きか |
|---|---|---|---|---|
| FAQ回答候補の提示 | 中 | 過去FAQがある | 人が確認可能 | 高い |
| 融資の自動承認 | 大 | 履歴あり | 顧客への影響が重大 | 初回PoCでは慎重 |
| 会議室利用の予測 | 小 | 予約ログあり | 小さい | 技術確認には適するが価値を要確認 |

PoC対象は、課題が重要であるだけでなく、限定条件で検証でき、結果から次の判断ができることが重要です。

## 3. PoCとは何か

PoC（Proof of Concept）は、限定された条件で「考え方や技術が有効か」を検証する取組です。完成品を作ることや、本番導入を既定路線にすることではありません。

| PoC | 本番導入 |
|---|---|
| 主要な不確実性を検証する | 継続的に業務価値を提供する |
| 対象・期間・データを限定できる | 全対象と例外を安定して扱う |
| 手作業を一部許容する場合がある | 運用、監視、障害対応が必要 |
| 不成立も有益な結論 | サービス水準と責任を負う |

良いPoCは成功を演出するものではなく、「導入」「追加検証」「保留」「中止」を区別できる証拠を集めます。

## 4. PoCを企画する

### 4.1 課題・仮説・成功条件

課題は現状の困り事、仮説は技術によって起こせる変化、成功条件はその仮説を採用できる基準です。

```text
課題：問い合わせ分類に時間がかかる
  ↓
仮説：分類AIで一次分類時間を30%短縮できる
  ↓
成功条件：時間、精度、重大見逃し、確認負荷、情報管理
  ↓
検証条件：対象、期間、比較方法、評価者、データ版
```

成功条件は一つの精度指標だけにしません。

| 区分 | 成功条件の例 |
|---|---|
| 業務効果 | 1件当たり一次分類時間を30%短縮する |
| 品質 | 業務上必要な分類精度を満たす |
| 重大リスク | 緊急案件の見逃し率を許容範囲内にする |
| 利用者負荷 | 確認・修正時間を含めても総時間が短縮する |
| 技術 | 想定件数を制限時間内に処理する |
| 統制 | 機密情報を規程と契約に従って扱える |
| 経済性 | 想定利用量で便益が運用費を上回る見込みがある |

### 4.2 検証条件を固定する

対象、期間、サンプル数、比較方法、評価者、データ版、除外条件を事前に定めます。結果を見た後で成功条件や除外条件を変えると、都合のよい事例だけが残り、検証の信頼性が下がります。変更が必要なら、理由と影響を記録し、探索的な結果と正式評価を分けます。

### 4.3 役割とスケジュール

| 役割 | 主な責任 |
|---|---|
| 業務責任者 | 課題、成功条件、導入判断 |
| 業務担当者 | 現行手順、例外、利用者評価 |
| データオーナー | データ利用の承認、条件確認 |
| データ主管組織・分析担当 | データ、評価設計、結果の妥当性 |
| IT部門 | 環境、連携、アクセス、運用評価 |
| 法務・セキュリティ | 契約、法令、リスク対策 |
| PoC責任者 | 日程、課題、変更、結果の統合 |

日程には、準備、データ確認、実施、評価、結果説明、データ廃棄まで含めます。

## 5. 事前準備と調整

PoCだから統制を省略してよいわけではありません。限定環境や疑似データを用いることで、検証目的を保ちながらリスクを抑えます。

### 事前チェック表

- データオーナーと試行的利用の許可
- 個人情報・機密情報・契約上の利用条件
- 社内IT環境、アカウント、アクセス権
- 外部サービスの保存場所、再学習利用、再委託、削除条件
- データ抽出、マスキング、匿名化、保管、廃棄
- 対象データの定義、品質、版、正解データ
- 実施体制、問い合わせ先、最終承認者
- 事故時の停止、報告、復旧手順
- 費用上限、利用量上限、終了条件

### 職場例：外部AIサービスのPoC

購買部が契約書要約を試す場合、実契約書を個人アカウントから入力してはいけません。データオーナー、法務、IT部門と、入力可能な文書、サービス側の保存・学習条件、アクセス権、出力の確認者、終了後の削除を調整します。目的が操作性の確認なら、まず架空契約書で試す選択肢もあります。

## 6. 実施と評価

実施中は、成功例だけでなく入力、処理、出力、例外、設定変更を記録します。

```text
計画した条件
   ↓
実施 ──→ 例外・変更を記録
   ↓
結果を成功条件ごとに比較
   ↓
失敗例と原因候補を分析
   ↓
本番との差・未確認事項を整理
```

| 評価領域 | 定量例 | 定性例 |
|---|---|---|
| 業務効果 | 時間短縮率、処理件数 | 作業の分かりやすさ |
| 品質 | 正答率、見逃し率、修正率 | 誤りの重大性、説明の納得感 |
| 運用 | 障害件数、確認時間 | 例外処理の難しさ |
| 技術 | 応答時間、可用性 | 既存画面との使い勝手 |
| 経済性 | 1件当たり費用、削減工数 | 費用仮定の確からしさ |

精度が高くても、本番データを継続取得できない、処理時間が長い、説明責任を満たせないなら導入不適合かもしれません。平均精度だけでなく、重大な失敗がどの条件で起きたかを確認します。

### 費用対効果の捉え方

```text
期待便益
  ＝ 削減時間 × 対象件数 × 人件費換算
    ＋ 品質向上・機会損失低減など

総費用
  ＝ 初期費用 ＋ 利用料 ＋ 連携・運用・監視・教育・確認の費用
```

仮定を明示し、過大な便益や見落とした運用費がないかを確認します。PoC時の無料枠や手作業支援を、本番費用の見積りから除外し忘れないようにします。

## 7. 本番との差を評価する

| 項目 | PoCで起こりやすい状態 | 本番で確認すべきこと |
|---|---|---|
| データ量 | 少量・選別済み | 全量、繁忙時、未知の入力 |
| データ品質 | 整備済み | 欠損、表記揺れ、遅延 |
| 利用者 | 協力的な少人数 | 習熟度の異なる全利用者 |
| 運用 | 専門家が随時支援 | 問合せ、監視、障害、変更管理 |
| 連携 | 手作業で入出力 | 認証、API、性能、再処理 |
| 費用 | 無料枠・短期間 | 継続利用、保守、教育、監査 |

小規模データで成功したことは、全社規模での性能・品質・運用を保証しません。差が大きい項目は、本格導入前の追加検証又は対策として明示します。

## 8. 結果を共有し、提案する

結果報告は、技術デモではなく意思決定資料です。

1. 検証目的、仮説、対象ユースケース
2. 対象データ、期間、比較方法、変更点
3. 成功条件と実績の比較
4. 確認できた業務効果と有効性
5. 失敗例、未確認事項、限界
6. 業務・技術・法務・運用上の課題と対策
7. 本番化に必要な体制、費用、日程
8. PoC環境と本番環境の差
9. 導入、追加検証、保留、中止の提案と理由

### 判断の分岐

```text
成功条件を満たしたか
  ├─ はい ─→ 本番との差と残存リスクは許容可能か
  │             ├─ はい → 導入計画を提案
  │             └─ いいえ → 対策又は追加検証
  └─ いいえ → 改善可能で、追加検証の価値があるか
                ├─ はい → 条件を見直して追加検証
                └─ いいえ → 保留又は中止
```

不成立という結果も、理由と条件を記録すれば組織のノウハウになります。同じ技術を別部門が重複して試すことを防ぎ、条件が変わったときの再検討材料にもなります。

## 9. 技術スキャニングを継続的な仕組みにする

技術動向の把握は、担当者が偶然見つけたニュースを読むだけでは偏ります。探索範囲、更新頻度、証拠の強さ、責任者を決め、候補を同じ基準で比較します。候補技術は「採用」だけでなく、「監視」「限定検証」「見送り」に分類し、前提が変わる時期を決めて再確認します。

| スキャン項目 | 記録する内容 | 判断への使い方 |
|---|---|---|
| 変化の種類 | 新機能、価格改定、廃止、規制、標準、脆弱性 | 機会だけでなく既存利用のリスクも捉える |
| 情報の時点 | 公開日、対象版、確認日 | 古い評価を現行版へ流用しない |
| 証拠の強さ | 公式仕様、第三者検証、自社再現、未検証の主張 | 主張と確認済み事実を分ける |
| 適用条件 | データ量、言語、業種、構成、地域 | 自社条件との距離を評価する |
| 成熟性 | 提供実績、互換性、サポート、更新方針 | 長期運用できるかを検討する |
| 撤退条件 | 価格上限、廃止予告、データ移行、代替技術 | ロックインと停止時の影響を抑える |
| 次回確認 | 担当者、期限、変化を検知する情報源 | 一度きりの調査で陳腐化させない |

```text
広く探索する
   ↓
重複を除き、出所・版・日付を記録
   ↓
業務課題との関連性で絞る
   ↓
証拠の強さと自社条件との差を評価
   ├─ 監視：今は条件が整わない
   ├─ 見送り：価値又は安全性が不足
   └─ 検証候補：重要な不確実性をPoCへ
                    ↓
            結果を技術台帳へ戻す
```

情報収集量を成果にしてはいけません。技術名の一覧ではなく、どの業務課題に関係し、何が未確認で、何が起きたら再評価するかまで残して初めて意思決定に利用できます。

## 10. 本番を代表するPoCを設計する

代表性とは、単にサンプル数が多いことではありません。本番で結果を左右する条件が評価データに含まれていることです。平均的な案件だけでなく、頻度は低いが影響の大きい案件、繁忙時、欠損、初めての利用者などを含めます。

| 本番の変動軸 | 問い合わせ分類PoCの層別例 | 含めない場合の危険 |
|---|---|---|
| 頻度 | 上位カテゴリ、少数カテゴリ | 多数派だけで平均精度が高くなる |
| 重大性 | 通常、緊急、法務関連 | 重大な見逃しを把握できない |
| 入力品質 | 定型文、略語、誤字、添付あり | 整備済みデータだけで成功する |
| 時間 | 通常時、月末、障害発生時 | ピーク時の遅延を見落とす |
| 利用者 | 熟練者、新任者、管理者 | 専門家の支援を本番でも期待してしまう |
| 連携 | 正常、タイムアウト、重複、再処理 | 例外時の二重登録や欠落を見落とす |

```text
本番母集団
  ├─ 多数・通常ケース ─────→ 無作為又は期間連続で抽出
  ├─ 少数・重要ケース ─────→ 意図的に追加
  ├─ 低品質・境界ケース ───→ 別枠で耐性を確認
  └─ ピーク・障害ケース ───→ 負荷／復旧試験
                    ↓
       層ごとの結果 ＋ 本番比率での全体結果
```

少数・重大ケースを多めに含めた場合、そのまま全体精度を計算すると本番比率とずれます。全体を推定する結果と、リスク確認のために意図的に集めた結果を分けて報告します。また、開発に用いたデータと正式評価データを分け、評価データを見ながら設定を調整した場合は別のデータで再評価します。

## 11. スケーリングギャップと総費用を見積もる

PoCから本番へ移ると、件数だけでなく、同時利用、利用者の多様性、監視時間、データ変化、障害時の責任が増えます。この差を**スケーリングギャップ**として明示します。

| ギャップ | PoCで隠れやすいこと | 本番見積りへ加えるもの |
|---|---|---|
| 容量・性能 | 順番に少量処理する | ピーク同時数、待ち行列、余裕率、再処理 |
| 可用性 | 担当者が手作業で復旧する | 冗長化、監視、当番、復旧目標 |
| データ | 固定した整備済みデータを使う | 継続取込、品質監視、変化時の再評価 |
| 人 | 熟練メンバーだけが利用する | 教育、問合せ、権限異動、操作ミス対策 |
| 統制 | 限定アカウントで試す | 全利用者の認証、ログ、監査、保存・廃棄 |
| 変更 | PoC中は版を固定する | API・モデル更新、回帰試験、移行、終了対応 |

総費用（TCO: Total Cost of Ownership）は購入価格やAPI利用料だけではありません。初期費用、継続費用、利用量に応じた変動費、内部要員の工数、リスク対策、撤退費用を対象期間で見積もります。

| 費用区分 | 具体例 | 見落としやすい点 |
|---|---|---|
| 初期 | 設計、データ整備、連携、移行 | 社内担当者の工数も費用である |
| 継続固定 | 保守、監視、ライセンス、教育 | 異動者向け教育が毎年発生する |
| 変動 | API、保存、通信、人による確認 | 利用増と再処理で単価以上に増える |
| 品質・統制 | 評価、監査、セキュリティ、事故対応 | モデルや規程変更時に再評価が必要になる |
| 撤退 | データ返却、代替移行、契約終了 | 出力形式と移行支援が契約にない場合がある |

### 職場例（計算）：問い合わせ分類AIの3年間の費用対効果

年間12,000件を1件8分、時間単価3,000円で分類している業務を考えます。AI導入後も人が確認するため1件3分かかるとすると、年間の時間便益は次のとおりです。

```text
年間便益
= 12,000件 × (8分 - 3分) ÷ 60分 × 3,000円
= 3,000,000円
```

初期の連携・移行・教育費を180万円、API、監視、品質評価、問合せ対応を含む年間継続費を165万円と見積もります。

| 指標 | 計算 | 結果 |
|---|---|---:|
| 1年目総費用 | 180万円 + 165万円 | 345万円 |
| 1年目純便益 | 300万円 - 345万円 | -45万円 |
| 3年間TCO | 180万円 + 165万円 × 3年 | 675万円 |
| 3年間総便益 | 300万円 × 3年 | 900万円 |
| 3年間純便益 | 900万円 - 675万円 | 225万円 |
| 3年間ROI | 225万円 ÷ 675万円 | 約33.3% |
| 初期費用の回収期間 | 180万円 ÷ (300万円 - 165万円) | 約1.33年 |

1年目だけでは費用超過ですが、仮定どおり3年間使えば純便益が見込めます。ただし、問い合わせ件数の減少、API価格の上昇、確認時間が3分を超える場合は結果が変わります。したがって、件数、確認時間、価格を感度分析し、「確認時間が何分を超えたら保留するか」のような再検討条件を置きます。品質低下や重大誤分類の損失を金額にできない場合は、無理に便益へ足さず、独立した必須条件として評価します。

## 12. ステージゲートと終了基準

PoCを始める前に、節目ごとの判断者、必要な証拠、進む条件、止める条件を決めます。終了基準には、成功して次段階へ進む条件だけでなく、安全性、費用、期限、データ取得不能などによる中止条件も含めます。

| ゲート | 判断すること | 進むための証拠 | 保留・中止の例 |
|---|---|---|---|
| G0 課題選定 | 検証する価値があるか | 基準値、利用者、期待便益 | 課題が小さい、責任者が不在 |
| G1 実施承認 | 安全かつ評価可能か | データ許可、評価設計、費用上限 | 利用許可なし、正解基準を作れない |
| G2 中間確認 | 継続に合理性があるか | 重大事故なし、データ品質、進捗 | 予算超過、重大リスク、前提崩壊 |
| G3 結果判定 | 仮説を支持したか | 事前の成功条件との比較 | 必須条件未達、結果を再現できない |
| G4 本番化承認 | 規模拡大に耐えるか | TCO、運用設計、負荷・障害試験 | 責任体制なし、残存リスクが過大 |

```text
課題候補
  ↓ G0: 検証価値
計画・準備
  ↓ G1: 許可と評価可能性
PoC実施 ── G2: 続行／修正／早期終了
  ↓
結果評価
  ↓ G3: 導入候補／追加検証／保留／中止
本番準備
  ↓ G4: 運用・TCO・規模の承認
本番化 ──→ 運用指標が閾値を外れたら縮小・停止・再評価
```

終了は敗北ではありません。例えば「緊急案件を1件でも見逃したら直ちに利用を停止し、原因確認まで再開しない」「4週間で必要データの利用許可が得られなければ中止する」と事前に決めれば、損失を限定できます。逆に、期限のたびに基準を緩めるとサンクコストに引きずられます。ゲートでは、既に使った費用ではなく、追加費用で得られる証拠と将来便益を比較します。

## 確認問題（本書オリジナル）

### 問1

生成AIによる文書要約PoCで、担当者が選んだ短い文書10件すべてを正しく要約できました。本番導入判断に不足する情報を挙げてください。

**解答例：** 対象選定の偏り、長文・表・画像・例外文書、評価基準、複数評価者の一致、誤要約の影響、機密性、処理時間、費用、利用者の確認負荷、本番規模、モデル変更時の再評価が不足しています。少数の選別済み文書では本番条件を代表しないためです。「10件全て成功したので導入する」のは標本の偏りと運用リスクを無視するため不適切です。「1件でも将来誤る可能性があるので中止する」のも、誤りの影響と人による確認などの対策を評価していないため不適切です。

### 問2

問い合わせ分類AIのPoCで分類精度は目標を達成しましたが、担当者の確認時間を含めると総作業時間が10%増えました。どのように提案しますか。

**解答例：** 業務効果の成功条件は未達と整理し、確認が増えた分類や画面操作を分析します。改善見込みと追加検証費用が妥当なら対象分類を限定して再検証し、見込みが乏しければ保留又は中止を提案します。技術精度と業務効果は別だからです。「精度を達成したので全面導入」は現場負荷を無視するため不適切です。「時間が増えたので直ちに技術全体を否定する」のも、限定適用や操作改善の可能性を調べていないため不適切です。

### 問3

ベンダー事例では需要予測により在庫を30%削減できたと説明されています。PoC候補にする前に何を確認しますか。

**解答例：** 事例の業種、商品特性、基準値、比較期間、需要変動、対象データ、削減と欠品の関係、利用した版、導入・運用費、自社データの取得可能性を確認します。事例の適用条件が自社と同じとは限らないためです。「著名企業の事例なので同じ効果を見込む」のは条件差を無視するため不適切です。「ベンダー情報は宣伝なので全て無視する」のも、公式仕様や検証条件を知る情報源まで捨てるため不適切です。

### 問4

問い合わせ分類AIは、選別した500件で精度目標を達成しました。しかし、月末ピークの負荷試験では応答時間が上限を超え、緊急案件の評価数は5件だけでした。3年間TCOには監視要員とモデル更新時の再評価費も含まれていません。G3の結果判定で何を提案しますか。

**解答例：** 全面導入には進めず、追加検証を条件付きで提案します。通常案件の精度という仮説は支持されましたが、本番を代表する重大案件の標本、ピーク性能、運用体制、TCOが不足しているためです。緊急案件を意図的に追加した独立評価、想定同時数での負荷・復旧試験、監視と再評価を含む費用見積りを次のゲート条件にします。改善策を含めても応答時間又は費用上限を満たさない場合は中止する終了基準も置きます。「500件で精度を達成したので導入する」のは代表性とスケーリングギャップを無視するため不適切です。「未確認事項があるので技術を直ちに永久却下する」のも、限定した追加検証で意思決定可能な証拠を得られるかを評価していないため不適切です。

## まとめ

- 技術動向は複数の情報源から継続的に収集し、証拠の強さ、版、自組織の条件、再確認時期を記録する。
- PoC対象は、業務価値があり、限定条件で主要な不確実性を検証できるユースケースから選ぶ。
- 課題、仮説、成功・中止条件、対象データ、役割、日程を実施前に定める。
- 本番を左右する通常・少数重大・低品質・ピーク条件を含め、層別に代表性を評価する。
- 結果は精度だけでなく、業務効果、品質、運用、リスク、スケーリングギャップ、TCOで評価する。
- ステージゲートごとに必要な証拠と終了基準を定め、導入、追加検証、保留、中止を判断する。
